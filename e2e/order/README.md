# 주문 생성 E2E 시나리오

실제로 띄운 7개 서비스에 **Gateway로 주문을 넣고, 응답과 각 서비스 DB 값을 함께 확인**합니다. 테스트 코드(Mock)로는 잡히지 않는 서비스 사이 계약·트랜잭션 문제를 보는 용도입니다. 손으로 따라 하는 순서는 [06 주문 흐름 수동 테스트 가이드](<../../docs/guide/06 주문 흐름 수동 테스트 가이드.md>)에 있습니다.

## 실행 (저장소 루트에서)

```bash
docker compose up -d postgres redis
sh ./gradlew bootJar
# eureka → user·hub·company·delivery·order → gateway 순으로 띄우기 (06 가이드 1.1)

python3 e2e/order/run.py             # 전체 19개 케이스 (약 2분, F7은 delivery-ms를 내렸다 다시 띄움)
python3 e2e/order/run.py S1 C2       # 고른 케이스만 (S8~S10은 S1, F3는 F2 뒤에)
python3 e2e/order/run.py --list      # 케이스 목록
python3 e2e/order/run.py cleanup     # 스크립트가 만든 업체·상품·재고·주문·배송 지우기
```

- 케이스마다 상품·재고를 새로 만들어 서로 영향을 주지 않습니다. 업체 두 곳은 실행마다 새로 만들고 comp02·comp03 소속을 연결합니다.
- 장애 케이스는 프로세스를 `SIGSTOP`으로 멈추거나(응답 없음) 내렸다가 다시 띄웁니다(꺼짐). 끝나면 되돌립니다.
- `.env`의 DB·MASTER 정보를 읽고 값은 출력하지 않습니다.
- 결과: `results/result.md`(케이스별 응답·기대·실제), `results/result.json`

- **F6·F7 통과**: E2가 PR #61(복원 요청을 `originalOperationId` 기준으로 변경, 결과를 모르면 같은 키로 차감 재전송해 확인)로 해결됨
- 남은 실패 G1 G2 G3 F8은 E3~E5이고, 담당자 확인 전까지 보류 중입니다.
- 트랜잭션 분리 전(E1 수정만)과 후 모두 15/19로 같습니다. 분리가 동작을 바꾸지 않았음을 확인했습니다.

발견한 문제 (자세한 값은 `results/result.md`)

| # | 문제 | 원인 | 영향 | 케이스 | 전달 | 상태 |
|---|---|---|---|---|---|---|
| E1 | **같은 키로 동시에 주문하면 재고가 여러 번 빠지고 배송이 여러 개 생김** | 이력(`p_order_histories`) 저장이 트랜잭션 커밋 때 반영돼, 유니크 제약 위반이 재고 차감·배송 생성 호출 **뒤에** 터짐. 4건은 500으로 롤백되지만 다른 서비스 작업은 남음 | 따닥 5번에 재고 15개 차감(정상 3), 주문 없는 배송 4건 | C2 | 다울 | ✅ 실험 브랜치에서 수정 |
| E2 | **재고 복원(보상)이 항상 실패** | order-ms는 `{orderId}`를 보내는데 hub-ms는 `{originalOperationId}`(원래 차감 작업 ID)를 요구 → 400 `INVALID_INPUT`. hub 복원 API 자체는 정상(올바른 본문으로 직접 호출하면 97→100) | 배송 단계에서 실패하면 주문은 `FAILED`인데 재고는 빠진 채 남음 | F6 F7 F8 | 다울·이찬 | ✅ PR #61 |
| E3 | 결과 모름 뒤 고아 배송 | 배송 생성이 타임아웃(2초)되면 주문은 실패 처리하지만, 멈췄던 delivery-ms가 재개되면 배송을 그대로 만듦 | `FAILED` 주문에 배송이 붙어 있음 | F8 | 다울·영은 | 보류 |

| E5 | 업체·상품 검증 없음 | order-ms가 company-ms를 부르지 않음 | 공급업체 소유가 아닌 상품도 주문·재고 차감됨. 없는 상품은 404가 아니라 재고 부족 409 | G2 G3 | 다울 | 보류 |
| E6 | 배송담당자 없음 정책 불일치 | delivery-ms는 담당자 없이 배송 생성, 07 서비스 정책은 "후보 없으면 404" | 문서와 동작이 다름 (동작은 합리적) | F4 | 영은 (문서) | 보류 |

- (해결 전 메모) E2는 orderId로 복원할 수 있게 hub-ms가 받거나, order-ms가 차감 응답의 `operationId`를 저장해 보내면 됩니다. 다만 E3처럼 차감 응답을 못 받은 경우(결과 모름)에는 `operationId`를 모르므로 **orderId(또는 차감 멱등키)로 복원**하는 쪽이 안전합니다.
- E1은 이력을 `saveAndFlush`로 바로 반영하고, 유니크 위반을 `DuplicateOrderRequestException` → 409로 바꿔 해결했습니다. 예외를 트랜잭션 안에서 잡아 `BusinessException`으로 던지면 rollback-only 때문에 500이 되므로, 트랜잭션 밖(order-ms `OrderExceptionHandler`, 분리 후에는 `TransactionTemplate` 밖)에서 처리합니다.
