# 상품 조회 최적화 레포트

> 대상: company-ms 상품 조회 (인기 상품 TOP 10 · 상품 상세 · 이름 검색) · 측정 2026-10-19 · 브랜치 `perf/product-query-cache` (실험용, dev 미반영) · 재현: [perf/product-query](<../../perf/product-query/README.md>)

## 0. 요약

**테스트 조건: 상품 100만 건 · 동시 사용자 50명(k6 VU 50) · API마다 30초씩 계속 조회** (워밍업 10초 별도)

동시 사용자 50명이 쉬지 않고 요청을 보낼 때 30초 동안 몇 건을 처리했고, 응답이 얼마나 걸렸는지입니다. p95·p99는 요청을 빠른 순으로 줄 세웠을 때 95%·99% 지점의 응답 시간입니다(p99 2.5ms = 요청 100건 중 99건이 2.5ms 안에 끝남). 사용자 수를 10~200명으로 바꾼 결과는 6장에 있습니다.

| S1 인덱스 X | 622건 | 19 | 2,531ms | 3,010ms | 3,090ms |

- 모든 구간 실패율 0%입니다.
- **인덱스만으로는 2배 이하**였습니다.
  - 인기 상품: 목록 쿼리는 0.25ms가 됐지만, 페이지 응답의 **전체 건수(count) 쿼리가 여전히 100만 행을 읽습니다**.
  - 이름 검색: 1~2글자 검색어는 **트라이그램 인덱스로 거를 수 없습니다**. 게다가 앱이 검색어를 파라미터로 보내 일반 계획이 쓰이면, 인덱스를 억지로 타서 **오히려 4~5배 느려집니다**.
  - 상품 상세는 원래 PK 조회라 인덱스와 무관합니다.
- **캐시가 결정적**이었습니다. DB까지 가는 일 자체를 없애서 수백~수천 배가 됐습니다.
- **레이어드 캐시(L1 추가)는 Redis 캐시보다 1.5~2.8배** 빨랐습니다. 같은 서버 메모리에서 바로 응답하니 Redis 왕복과 JSON 역직렬화가 빠지기 때문입니다.
- **사용자를 10명 → 200명으로 늘리면** S1은 처리량이 그대로(인기 상품 초당 24건)이고 p99만 731ms → 8,878ms로 늘었습니다. S4는 상세 기준 초당 1.7만 → 6.4만 건으로 함께 늘었습니다. 다만 S4 검색은 200명에서 캐시 스탬피드로 커넥션 풀이 고갈돼 p99 18.5초까지 무너졌습니다(6장).
- 상세는 조회수 쓰기가 병목이었습니다. 조회수를 Redis에 모아 5초마다 반영하자 DB UPDATE가 **요청 1건당 1번(11.4만 번)에서 상품 1개당 5초에 1번(약 2.4만 번)**으로 줄었습니다.

## 2. 단계

| 단계 | 인덱스 | 캐시 | 조회수 |
|---|---|---|---|
| S1 | 없음 (PK, `company_id`만) | 없음 | 요청마다 DB `UPDATE +1` |
| S2 | `(view_count DESC, id) WHERE deleted_at IS NULL` + `pg_trgm` GIN `lower(name)` | 없음 | 요청마다 DB `UPDATE +1` |
| S3 | S2와 같음 | Redis (상세 TTL 5분, 목록·검색 30초) | Redis 누적 → 5초마다 DB 반영 |
| S4 | S2와 같음 | Caffeine L1(10초, 최대 1만 건) → Redis L2 | Redis 누적 → 5초마다 DB 반영 |

- 단계는 설정 `PRODUCT_CACHE_MODE`(none/redis/layered)와 인덱스 SQL로 바꿉니다. 코드는 그대로입니다.
- 상품을 수정하거나 삭제하면 상세 캐시를 지웁니다. 목록·검색 캐시는 지우지 않고 30초 TTL로만 갱신합니다.

## 3. 인기 상품 TOP 10 (`GET /api/v1/products?sort=viewCount,desc&size=10`)

| 단계 | 30초 처리 건수 | req/s | 평균 | p50 | p95 | p99 | 최대 | DB 전체 스캔 | DB가 읽은 행 | Redis hit |
|---|---|---|---|---|---|---|---|---|---|---|
| S1 | 773 | 24 | 2,010ms | 2,027ms | 2,401ms | 2,502ms | 3,667ms | 3,134 | 15.5억 | - |
| S2 | 1,591 | 51 | 958ms | 954ms | 1,150ms | 1,236ms | 1,770ms | 3,237 | 16.0억 | - |
| S3 | 1,187,647 | 39,586 | 1.2ms | 1.2ms | 1.6ms | 2.2ms | 1,643ms | 101 | 5386.5만 | 118.8만 |
| S4 | 2,781,238 | 92,705 | 0.5ms | 0.5ms | 0.9ms | 1.4ms | 48.8ms | 3 | 239.1만 | 150 |

**S1 → S2: 인덱스가 반쪽만 통했습니다.** 실행 계획(`results/S*-explain.txt`)을 보면 이렇습니다.

| 쿼리 | S1 | S2 |
|---|---|---|
| 목록 10건 (`ORDER BY view_count DESC, id LIMIT 10`) | 전체 스캔 + top-N 정렬 **106ms** | 인덱스 앞에서 10건만 **0.25ms** |
| 전체 건수 (`count(*)`, 페이지 응답 `totalElements`) | 전체 스캔 78ms | **여전히 전체 스캔 68ms** |

- 페이지 응답은 공통 `PageResponse`라서 전체 건수를 항상 같이 계산합니다. S2에서도 요청당 전체 스캔이 한 번씩 남아(3,237번) DB가 16억 행을 읽었습니다.
- **"인덱스를 걸었는데 왜 안 빨라지지?"의 답이 count 쿼리였습니다.** 개선안은 7장에 있습니다.

**S2 → S3: 캐시가 DB를 거의 없앴습니다.**
- TOP 10은 모두에게 같은 결과라 키가 하나입니다. 30초 TTL 동안 DB는 한 번만 읽으면 됩니다.
- 그런데 측정 중 전체 스캔이 101번 나왔습니다. TTL이 끝나는 순간 50명(VU)이 동시에 캐시를 놓쳐 **모두 DB로 갔습니다**(목록 + count 2쿼리 × 약 50명). 이것이 **캐시 스탬피드**입니다(6·7장).

**S3 → S4: Redis 왕복을 없앴습니다.**
- Redis hit이 118.8만에서 150으로 줄었습니다. 요청은 서버 메모리(L1)에서 끝나고, Redis는 L1이 만료될 때(10초)만 봅니다.
- p95 1.6ms → 0.9ms, 처리량 2.3배입니다.

## 4. 상품 상세 (`GET /api/v1/products/{id}`, 조회할 때마다 조회수 +1)

| 단계 | 30초 처리 건수 | req/s | 평균 | p50 | p95 | p99 | 최대 | DB 인덱스 조회 | DB UPDATE | Redis hit |
|---|---|---|---|---|---|---|---|---|---|---|
| S1 | 114,392 | 3,811 | 13.1ms | 9.3ms | 30.8ms | 46.8ms | 142ms | 34.2만 | 11.4만 | - |
| S2 | 108,474 | 3,614 | 13.8ms | 10.0ms | 31.9ms | 48.2ms | 122ms | 32.3만 | 10.8만 | - |
| S3 | 857,980 | 28,597 | 1.7ms | 1.7ms | 2.2ms | 3.0ms | 15.1ms | 2.9만 | 2.8만 | 174.4만 |
| S4 | 1,262,399 | 42,078 | 1.2ms | 1.1ms | 1.7ms | 2.5ms | 22.3ms | 2.4만 | 2.4만 | 131.7만 |

- **S1 = S2**: 상세는 원래 PK 조회라 추가 인덱스와 상관없습니다(차이는 측정 오차 범위).
- **S1의 병목은 읽기가 아니라 쓰기**였습니다. 요청 1번에 쿼리 4번(상품·업체 조회, `UPDATE`, 다시 조회)이고, 인기 상품에 몰리면 같은 행의 `UPDATE`가 행 잠금을 기다립니다. p50 9.3ms와 p99 46.8ms 사이의 큰 차이는 이 대기 때문으로 보입니다.
- **S3·S4: 읽기는 캐시, 쓰기는 Redis 누적으로 뺐습니다.**
  - 조회수 키에 누적값을 두고, Lua 스크립트 하나로 `INCR`와 "반영 대상 등록"을 Redis 왕복 1번에 처리합니다.
  - 응답의 조회수는 Redis 누적값이라 **요청마다 정확**합니다.
  - DB에는 5초마다 바뀐 상품만 한 번씩 `UPDATE ... WHERE view_count < :누적값`으로 반영합니다.
  - DB `UPDATE`가 11.4만 번에서 2.4~2.8만 번으로 줄었습니다. 이것도 요청 처리 중이 아니라 백그라운드에서 일어납니다.
- 다른 API보다 배수가 작은 이유는 상세에는 요청마다 Redis 쓰기(조회수)가 반드시 한 번 남기 때문입니다.

## 5. 이름 검색 (`GET /api/v1/products?name=…&size=10`, 기본 정렬 최신순)

| 단계 | 30초 처리 건수 | req/s | 평균 | p50 | p95 | p99 | 최대 | DB 전체 스캔 | DB가 읽은 행 | Redis hit |
|---|---|---|---|---|---|---|---|---|---|---|
| S1 | 622 | 19 | 2,514ms | 2,531ms | 3,010ms | 3,090ms | 3,176ms | 2,482 | 12.4억 | - |
| S2 | 643 | 20 | 2,428ms | 2,604ms | 3,401ms | 3,580ms | 4,245ms | 0 | 0 | - |
| S3 | 657,731 | 19,540 | 2.4ms | 1.2ms | 1.8ms | 2.5ms | 4,904ms | 0 | 0 | 65.8만 |
| S4 | 1,839,266 | 53,833 | 0.8ms | 0.5ms | 0.9ms | 1.3ms | 6,680ms | 0 | 0 | 3,626 |

**S1 → S2: 인덱스를 걸었는데 오히려 조금 느려졌습니다.** 검색어 길이와 쿼리 계획 방식에 따라 결과가 갈립니다(인덱스가 있는 상태의 검색 쿼리 실행 계획).

| 검색어 | 값을 넣어 실행 (psql) | 앱처럼 파라미터로 실행 (generic plan) |
|---|---|---|
| 고등어 (3글자) | 트라이그램 인덱스, **21ms** (S1 85ms) | 트라이그램 인덱스, **14ms** |
| 사과 (2글자) | 전체 스캔, 84ms | 인덱스 전체를 읽고 **97만 행 재확인, 387ms** |
| 배 (1글자) | 전체 스캔, 78ms | 인덱스 전체를 읽고 **95만 행 재확인, 358ms** |

- `pg_trgm`은 3글자 단위로 쪼개서 찾습니다. 그래서 **2글자 이하 검색어는 인덱스로 거를 수 없습니다.** 한글이라서 안 된 것은 아닙니다("고등어"는 인덱스를 썼습니다).
- 값을 직접 넣으면 PostgreSQL이 이 사실을 알고 전체 스캔을 고릅니다.
- 앱(JPA → JDBC)은 검색어를 **파라미터(`?`)로 보냅니다.** 같은 쿼리가 반복되면 PostgreSQL은 검색어를 보지 않는 **일반 계획(generic plan)**으로 바꿀 수 있습니다. 그러면 1~2글자에도 인덱스를 탄 뒤 거의 모든 행을 다시 확인해, 전체 스캔보다 4~5배 느려집니다.
- S2에서 DB 전체 스캔이 0번, 인덱스 조회만 1,286번으로 집계된 것이 이 현상입니다. 품목 40종 중 3글자 이상은 소수라, 부하 대부분이 이 느린 경로를 탔습니다.
- **인덱스는 "걸면 빨라진다"가 아니라 "쿼리 모양과 입력 분포에 맞아야 빨라진다"**는 사례입니다.

**S3 → S4**: 검색 결과(페이지 JSON)가 커서 Redis 왕복과 역직렬화 비용이 큽니다. 그래서 L1의 이득(2.8배)이 세 API 중 가장 컸습니다.

**주의할 점**: S3 평균(2.4ms)이 p95(1.8ms)보다 큽니다. 캐시가 만료되는 순간 몇 요청이 S1처럼 2~3초 걸리기 때문입니다(6·7장 캐시 스탬피드).

| 200명 | 717건 | 17 | 11,891ms | 12,040ms | 12,919건 | 278 | 3.5ms | 18,510ms (실패 0.02%) |

**읽는 법**

- **S1은 사용자를 늘려도 처리량이 그대로이고, 응답만 늘어납니다.**
  - 인기 상품은 10명이든 200명이든 초당 24건입니다. p99만 731ms에서 8,878ms로 12배 늘었습니다.
  - DB가 이미 한계라서, 사용자를 더 받으면 앞사람을 기다리는 줄만 길어집니다(처리량 고정, 대기 시간이 사용자 수에 비례).
  - 상세도 초당 약 3,700건에서 늘지 않고, p99는 4.2ms에서 190ms가 됐습니다(조회수 UPDATE 행 잠금 대기).
- **S4는 사용자를 늘리면 처리량도 같이 늘어납니다.**
  - 상세는 10명 1.7만 → 200명 6.4만 req/s입니다. 200명에서도 p99는 7.1ms입니다.
  - 인기 상품은 100명 근처에서 초당 약 9.5만 건으로 포화합니다. 이 노트북 한 대에서 k6와 앱이 CPU를 나눠 쓰는 한계로 보입니다.
- **S4 이름 검색은 200명에서 무너졌습니다.** 같은 S4인데 초당 278건, p99 18.5초, 실패 0.02%입니다.
  - 서버 로그: `HikariPool-1 - Connection is not available, request timed out after 30004ms (total=10, active=10, idle=0, waiting=111)`
  - 원인은 **캐시 스탬피드 + 느린 원본 쿼리 + 작은 커넥션 풀**이 겹친 것입니다.
    1. 검색 캐시는 검색어마다 30초 TTL입니다. 만료되는 순간 그 검색어를 기다리던 사용자들이 동시에 DB로 갑니다.
    2. 그 쿼리가 5장의 느린 경로(1~2글자 검색어 + generic plan, 약 400ms)입니다. 측정 30초 동안 인덱스로 읽은 행이 9.8억에 이릅니다.
    3. 커넥션 10개가 400ms씩 붙잡히자 대기열이 111명까지 쌓였고, 30초를 넘긴 요청이 실패했습니다.
    4. 그동안 다른 사용자도 응답을 못 받아 처리량 전체가 무너졌습니다(k6 VU는 응답을 받아야 다음 요청을 보냅니다).
  - 100명에서 처리량이 50명보다 낮았던 것(5.4만 → 3.1만)도 같은 현상이 작게 나타난 것입니다.
- **교훈: 캐시는 평균을 빠르게 하지만, 캐시가 비는 순간의 원본 비용이 그대로 꼬리 지연(p99)과 장애가 됩니다.** 캐시를 붙여도 원본 쿼리 최적화와 스탬피드 방지가 함께 필요합니다.

## 7. 정리와 다음 개선

**무엇이 효과가 있었나**

| 대책 | 효과 | 비용·위험 |
|---|---|---|
| 정렬 인덱스 `(view_count DESC, id)` | 목록 쿼리 106ms → 0.25ms | 조회수가 바뀔 때마다 인덱스도 고쳐야 해서 쓰기 비용이 늘어납니다(HOT update 불가). S3·S4처럼 조회수를 모아 반영하면 줄어듭니다 |
| 트라이그램 인덱스 | 3글자 이상 검색만 4~6배 | 1~2글자는 오히려 느려짐(generic plan). 인덱스 크기·쓰기 비용 |
| Redis 캐시 | 수백~1,650배 | 목록 최대 30초, 상세 수정 전 값 없음(수정 시 삭제). Redis 장애 시 DB로 몰림 |
| L1 Caffeine 추가 | Redis 대비 1.5~2.8배 | 서버가 여러 대면 다른 서버의 L1은 지워지지 않아 최대 10초 옛 값. 서버 메모리 사용 |
| 조회수 Redis 누적 | 상세 쓰기 병목 제거, DB UPDATE 약 1/5 | Redis가 반영 전에 사라지면 최대 5초치 조회수 유실 |

**다음에 해 볼 것**

1. **count 쿼리 없애기**: 인기 상품은 전체 건수가 필요 없습니다. `Slice`(다음 페이지 유무만)나 추정 건수(`pg_class.reltuples`)를 쓰면 S2 단계만으로도 큰 개선이 예상됩니다. 공통 `PageResponse`를 건드리는 일이라 팀 합의가 필요합니다.
2. **캐시 스탬피드 막기 (가장 시급, → S5 hot 모드로 구현, 아래 결과)**: 6장의 200명 장애가 실제로 일어났습니다. `@Cacheable(sync = true)`로 같은 키는 한 서버에서 한 번만 원본을 읽게 하고(레이어드 캐시는 키별 잠금 구현 필요), 인기 키는 만료 전에 미리 갱신하거나 TTL에 무작위 오차를 줍니다. 커넥션 풀 대기 시간(30초)도 짧게 줄여 빨리 실패하게 합니다.
3. **짧은 검색어**: 최소 3글자로 제한하거나, 2글자 이하는 접두어 검색(`name LIKE '사과%'` + B-tree)으로 나눕니다. 일반 계획 문제는 `plan_cache_mode = force_custom_plan`으로 피할 수 있지만 매번 계획을 세우는 비용이 듭니다. 본격적인 검색은 Elasticsearch 같은 검색 엔진 영역입니다.
4. **여러 서버의 L1 무효화**: Redis Pub/Sub로 수정·삭제를 알리면 다른 서버의 L1도 지울 수 있습니다.
5. **캐시하지 않은 것**: 주문 검증용 내부 API(`/internal/v1/products/{id}`)는 주문 시점 단가를 저장하므로 캐시하지 않았습니다. 오래된 단가가 들어가면 주문 금액이 틀려집니다.

### S5: 데이터별로 캐시 위치를 나눈 hot 모드 (P03, 측정 2026-10-21)

S4는 TOP 10·상세·검색을 모두 같은 방식(L1 10초 → Redis → DB)으로 담았습니다. 그래서 위 세 문제가 생겼습니다: TOP 10은 TTL이 끝날 때마다 비었다가 다시 채워지고(3장), 검색은 캐시가 만료되는 순간 몰리고(6장), 검색 결과가 L1을 채우면 TOP 10·상세가 밀려납니다. S5는 **데이터 성격에 맞춰 담을 곳을 나누고, 비우지 않고 덮어쓰게** 바꿨습니다.

| 데이터 | S4 | S5 (`PRODUCT_CACHE_MODE=hot`) |
|---|---|---|
| TOP 10 순위 | 목록 캐시(30초), 만료되면 DB에서 정렬 + count | Redis Sorted Set. 조회수를 올리는 Lua에서 점수도 같이 덮어씀(실시간) |
| TOP 10 상품 | L1 + Redis (만료 시 비움) | **L1 스냅샷을 5초마다 새로 만들어 덮어씀** (비는 순간 없음, DB·Redis 안 감) |
| 그 밖의 상세 | L1 + Redis | Redis만 (5분) |
| 검색·목록 | L1 + Redis (30초) | Redis만 (30초) + **키 단위 single-flight** (같은 검색어 동시 miss는 DB 1번) |

- `@Cacheable(sync = true)`만으로는 부족했습니다. Spring Data Redis 기본 writer는 잠금이 없어 각자 DB로 가고, 잠금 writer는 캐시 이름 단위로 잠가 다른 검색어까지 한 줄로 세웁니다. 그래서 서버 안에서 키별로 한 번만 읽게 했습니다.
- TOP 10 응답의 `totalElements`는 스냅샷 크기(최대 10)입니다. 전체 count 쿼리를 없앴습니다. URL·응답 모양은 그대로입니다.

**측정**: 같은 노트북에서 S4와 S5를 연달아 잼 (조건은 1장과 같음, 결과 `perf/product-query/results/p03/`). 새로 잰 S4는 VU 50 기준 3~5장 수치와 5% 안쪽으로 같았습니다.

| API | 동시 사용자 | S4 req/s | S5 req/s | S4 p99 / 최대 | S5 p99 / 최대 | DB 순차 스캔 (S4 → S5) |
|---|---|---|---|---|---|---|
| TOP 10 | 50명 | 95,656 | 96,663 | 1.3ms / 15ms | 1.2ms / 11ms | 22번 (1,902만 행) → **0번** |
| TOP 10 | 200명 | 98,445 | 94,641 | 5.5ms / 28ms | 5.8ms / 37ms | 13번 (927만 행) → **0번** |

| 검색 | 50명 | 50,356 | 34,214 (68%) | 1.7ms / 4.8초 | 2.7ms / 0.9초 | 0 → 137번 |

| API | 동시 사용자 | S1 | S2 | S5 | 배수 |
|---|---|---|---|---|---|
| TOP 10 | 50명 | 24 req/s, p99 2.5초 | 51 req/s, p99 1.2초 | 96,663 req/s, p99 1.2ms | S1 대비 약 4,000배 |
| TOP 10 | 200명 | 24 req/s, p99 8.9초 | — | 94,641 req/s, p99 5.8ms | 약 3,900배 |
| 상세 | 50명 | 3,811 req/s, p99 47ms | 3,614 req/s, p99 48ms | 24,817 req/s, p99 3.4ms | 약 6.5배 |

- 검색 배수는 k6가 검색어 40종을 앞쪽에 몰리게 보내 캐시가 잘 맞는 조건이라 큽니다. 검색어가 다양하면 훨씬 작아집니다.
- 상세는 S1·S2가 요청마다 DB UPDATE를 했으므로, 배수에 조회수 Redis 누적 효과도 섞여 있습니다.

**읽는 법**

- **TOP 10: 처리량은 같고 DB 부하가 0이 됐습니다.** S4는 30초 동안 목록 캐시가 만료될 때마다 DB가 100만 행을 전체 스캔했습니다(50명에서 22번). S5는 스냅샷을 덮어쓰기만 해서 측정 중 DB·Redis를 한 번도 거치지 않았습니다. 사용자 응답은 이미 1ms 수준이라 차이가 없지만, 서버를 늘리거나 DB가 바빠도 TOP 10이 영향을 받지 않습니다.
- **검색 200명: S4는 다시 무너졌고 S5는 버텼습니다.** S4는 p99는 5.6ms인데 최대 19.5초, 처리량 7,861 req/s였습니다. 일부 요청이 스탬피드에 걸려 20초 가까이 묶이는 동안 그 VU가 다음 요청을 못 보낸 것입니다(6장과 같은 현상. 6장은 278 req/s로 더 심했고, 만료 시점에 따라 흔들립니다). S5는 최대 1.1초, 5.6배 처리량입니다.
- **대가: 상세 -27~35%, 검색 50명 -32%.** L1을 TOP 10에만 쓰고 나머지는 Redis로 보내면서 요청마다 Redis 왕복과 역직렬화가 다시 생겼습니다. 계획에서 예상한 트레이드오프였지만, 상세는 목표(S4의 90% 이상)에 못 미쳤습니다. 검색 50명은 예상치(S3 19,540)보다는 높았습니다.
- **S5 검색의 DB 순차 스캔(50명 137번)**: 검색어별 캐시가 miss될 때 원본 쿼리가 일부 순차 스캔으로 실행된 것입니다. single-flight로 검색어당 1번으로 줄었을 뿐, 원본 쿼리 자체(짧은 검색어·count)는 이번 범위에서 고치지 않았습니다(다음에 해 볼 것 1·3번).
- 한 번씩만 잰 결과라 몇 % 차이는 오차일 수 있습니다. 5.6배·0번 같은 큰 차이만 결론으로 봅니다.

| 대책 | 효과 | 비용·위험 |
|---|---|---|
| TOP N L1 스냅샷 덮어쓰기 + 순위 ZSET | TOP 10 DB 스캔 0번 (만료 순간이 없어짐) | 순위·상품 정보가 최대 5초 늦음. 서버가 여러 대면 다른 서버 스냅샷은 다음 갱신(5초)까지 옛 값 |
| 키 단위 single-flight | 검색 200명 처리량 5.6배, 최대 지연 19.5초 → 1.1초 | 서버마다 1번씩은 DB에 감. 원본 쿼리가 느리면 기다리는 요청도 같이 느림 |
| 상세·검색 L1 제거 | 검색 결과가 L1을 채워 TOP 10·상세를 밀어내는 문제 제거 | 상세 처리량 -27%, 검색(50명) -32% |

남은 과제: 상세 처리량 회복(상세 전용 크기 제한 L1을 다시 둘지), 짧은 검색어·count 원본 쿼리 최적화, 커넥션 풀 대기량(Hikari waiting) 측정.
