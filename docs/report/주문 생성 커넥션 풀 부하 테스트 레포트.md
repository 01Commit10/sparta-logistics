# 주문 생성 커넥션 풀 부하 테스트 레포트

> 대상: order-ms `POST /api/v1/orders` (주문 생성) · 측정 2026-10-20 · 브랜치 `perf/order-create-tx` (실험용, dev 미반영) · 재현: [perf/order-create](<../../perf/order-create/README.md>)

## 0. 요약

**질문**
- 주문 생성은 트랜잭션 하나 안에서 원격 호출(재고 조회·차감, 배송 생성)을 합니다.
- 블랙프라이데이처럼 주문이 한꺼번에 몰리면 DB 커넥션 풀이 언제, 얼마나 고갈될까요?
- Hikari 풀을 키우는 것과 트랜잭션을 나누는 것 중 무엇이 효과가 있을까요?

**조건**
- 평소 초당 200건으로 보내다가 10초 만에 **초당 800건으로 급증**시키고, 60초 유지한 뒤 평소로 돌아갑니다.
- 800은 분리 전 구조의 처리 한계(초당 약 540건)의 1.5배입니다.
- 시나리오는 두 가지입니다. **A**는 주문 생성만 보내고, **B**는 주문 생성과 함께 주문 조회를 초당 200건씩 보냅니다.

| 단계 | order-ms 코드 | delivery-ms 코드 | order-ms 풀 | 최고 부하 때 처리량 | 생성 p99 | order-ms 풀 고갈 | **막힌 곳** (풀 대기 최대) | B: 조회 p99 (평소 → 최고 부하) |
|---|---|---|---|---|---|---|---|---|
| 1 | 분리 전 | 분리 전 | 10 | 540/s | 6,310ms | **81초** | order-ms 풀 (190) | 1.4ms → **5,700ms** |
| 2 | 분리 전 | 분리 전 | 20 | **620/s** (+15%) | **5,711ms** | 76초 | order-ms 풀 (180) | 1.4ms → 5,257ms |
| 3 | 분리 후 | 분리 전 | 10 | 446/s | 7,188ms | 62초 | **delivery-ms 풀** (174) | 1.8ms → 6,360ms |
| 4 | 분리 후 | 분리 전 | 20 | 469/s | 6,777ms | **0초** | **delivery-ms 풀** (175) | 1.9ms → 6,254ms |
| 5 | 분리 후 | **분리 후** | 10 | 458/s | 6,859ms | 81초 | **order-ms 풀** (179) | 2.5ms → 6,773ms |
| 6 | 분리 후 | **분리 후** | 20 | 470/s | 6,963ms | 7초 | **hub-ms 풀** (177) | 2.0ms → 6,059ms |

(처리량·생성 p99·고갈·막힌 곳은 A, 조회는 B 기준. 모든 측정에서 응답 실패율은 0%입니다.)

> **주의**: 측정 사이에 주문·배송·재고 작업 데이터를 지우지 않아, 뒤 단계일수록 큰 테이블에서 측정했습니다(1단계 시작 때 거의 0행 → 6단계 때 테이블마다 약 80만 행). DB 캐시(`shared_buffers` 128MB) 적중률도 85.9%까지 떨어져 있었습니다. 단계 사이 비교에는 이 차이가 섞여 있습니다(9장).

**결론**
1. **분리 전에는 order-ms 풀이 병목이었습니다.**
   - 주문 1건이 커넥션을 쥐는 시간은 18.6ms이고, 풀 10개로 처리할 수 있는 한계는 `10 ÷ 18.6ms ≈ 초당 538건`입니다. 실측도 540건이었습니다.
   - 부하가 이 한계를 넘는 순간(급증 5초째)부터 81초 동안 커넥션 10개가 모두 사용 중이었고, 커넥션을 기다리는 요청이 190개였습니다.
2. **풀을 2배로 키워도 처리량은 15%만 늘었습니다.**
   - 커넥션을 쥔 채 원격 호출을 기다리는 구조라서, 동시에 일하는 수가 늘자 원격 호출이 느려졌습니다.
   - 그 결과 1건당 점유 시간이 18.6ms에서 32.1ms로 늘었습니다.
3. **트랜잭션을 나누자 order-ms 풀 고갈은 사라졌지만(4단계 0초), 처리량은 늘지 않았습니다.**
   - 병목이 **delivery-ms 풀**로 옮겨 갔습니다. 계산상 한계 `10 ÷ 22.5ms ≈ 초당 444건`이 실측 446건과 맞습니다.
   - delivery-ms도 트랜잭션 안에서 원격 호출을 5번 하는 같은 구조였습니다.
4. **delivery-ms도 같은 방식으로 나누자(5·6단계), 병목이 다시 다음 서비스로 옮겨 갔습니다.**
   - 5단계 (order 풀 10): 주문 1건이 트랜잭션 3번 × 7.3ms를 쓰는 **order-ms 풀**이 다시 막혔습니다(한계 `10 ÷ 21.9ms ≈ 457/s`).
   - 6단계 (order 풀 20): 주문 1건마다 3번 불리는 **hub-ms 풀**(재고 조회·차감, 경로 조회)이 막혔습니다(한계 `10 ÷ (3 × 7.0ms) ≈ 476/s`).
   - **풀 10개짜리 서비스가 주문 1건마다 커넥션을 약 21ms 쓰는 곳이 하나라도 있으면, 처리량은 약 460/s에서 막힙니다.** 3~6단계의 처리량이 모두 446~470/s인 이유입니다.
   - 다른 원인이 아님도 확인했습니다. DB CPU는 15코어 중 약 2개분만 썼고, 커밋 동기화를 꺼도(`synchronous_commit=off`) 처리량이 4%만 늘었습니다.
5. **주문 조회는 모든 단계에서 1~2ms → 5~6초로 함께 느려졌습니다.**
   - 4·6단계처럼 order-ms DB 풀이 비어 있어도 마찬가지입니다. 조회와 생성이 **Tomcat 요청 스레드 200개**를 같이 쓰기 때문입니다.
   - 커넥션 풀만 지켜서는 장애가 다른 기능으로 번지는 것을 막을 수 없습니다.

**측정 환경 보정 (4단계 공통 적용)**
- macOS의 임시 포트(약 1.6만 개)와 TIME_WAIT(30초) 때문에 초당 600건부터 연결 자체가 실패했습니다(`can't assign requested address`). 이대로는 "풀 고갈"과 "노트북 포트 고갈"이 섞입니다.
  - `sysctl net.inet.ip.portrange.first=10000 net.inet.tcp.msl=1000`으로 넓혔습니다.
- Feign 기본 클라이언트(JDK `HttpURLConnection`)는 대상당 연결을 5개만 재사용해서, 부하가 걸리면 연결을 계속 새로 만듭니다.
  - 모든 서비스를 `-Dhttp.maxConnections=200`으로 띄웠습니다. 운영이라면 커넥션 풀이 있는 HTTP 클라이언트로 바꿔야 합니다(8장).

모두 한 대에서 돌린 측정이라 절대값보다 **단계 사이의 비율과 병목이 어디로 옮겨 가는지**를 봐야 합니다.

## 2. 단계와 부하

### 2.1 코드: 분리 전 / 분리 후

두 버전 모두 E1(같은 멱등키 동시 요청) 수정을 포함합니다. 이력을 `saveAndFlush`로 저장하고, 같은 키가 이미 처리 중이면 409로 거절합니다.

```
분리 전 (1·2단계): 트랜잭션 1개 = 커넥션 1개를 끝까지 쥠
[ 이력 저장 · 재고 조회(원격) · 주문 저장 · 재고 차감(원격) · 배송 생성(원격) · 확정 ] → 커밋

분리 후 (3·4단계): 짧은 트랜잭션 3개, 원격 호출은 트랜잭션 밖
[TX① 이력 선점] 재고 조회(원격) [TX② 주문 저장] 재고 차감(원격) · 배송 생성(원격) [TX③ 확정]
```

- 분리 후 `OrderService.createOrder`는 `@Transactional(propagation = NOT_SUPPORTED)`이고, 각 단계를 `TransactionTemplate`으로 실행합니다(hub-ms `InventoryStockService`와 같은 방식).
- **delivery-ms 분리 (5·6단계)**
  - `DeliveryCommandService.createDelivery`에 `@Transactional(propagation = NOT_SUPPORTED)`를 붙였습니다.
  - 원격 조회 5번(업체 2, 경로, 담당자, 이름)은 트랜잭션 없이 하고, 저장은 `deliveryRepository.save`의 짧은 트랜잭션 하나(배송 + 구간)로 끝납니다.
  - 검증: "원격 조회 중에는 트랜잭션이 열려 있지 않다"는 테스트를 새로 넣었습니다(Red는 5번 모두 트랜잭션 안 → Green). E2E도 15/19로 같습니다.
  - delivery-ms는 영은님 담당이라 실험 브랜치에만 넣었습니다.
- 실패하면 보상(재고 복원)은 트랜잭션 밖에서 하고, 실패 기록은 TX③에서 남깁니다.
- 검증:
  - order-ms 단위 테스트 33개가 통과합니다. "원격 호출 중에는 트랜잭션이 열려 있지 않다"는 테스트를 새로 넣었습니다.
  - 실제 서비스 E2E는 분리 전과 같은 15/19입니다. 실패한 4개는 보류 중인 E3~E5이고, C1·C2 동시성 케이스는 통과합니다.

### 2.2 부하 모양 (블랙프라이데이)

```
초당 주문
 800 |          ┌──────────────── 60초 ────────────────┐
     |         /                                         \
 200 |────────/                                           \────────
     0       30  40                                      100 110     140초

```

- **A**: 위 모양으로 주문 생성만 보냅니다.
- **B**: A + 주문 단건 조회 `GET /api/v1/orders/{id}`를 140초 동안 **초당 200건 일정하게** 보냅니다. 조회는 같은 order-ms의 커넥션 풀과 Tomcat 스레드를 씁니다.
- 매 요청 새 멱등키를 씁니다. 측정 전 15초 워밍업(기록 안 함)을 합니다.
- 수집 지표:
  - k6: 요청별 응답 시간, 응답 코드, 보내지 못한 요청(`dropped_iterations`)
  - 서비스별 Hikari: active·idle·pending·timeout, 커넥션 1회 점유 시간(`hikaricp.connections.usage`), 대여 대기 시간(`acquire`)
  - Tomcat 사용 중 스레드, `pg_stat_activity` (1초 간격)

## 3. DB 커넥션 풀 계산

### 3.1 풀 한 개가 버티는 처리량 (리틀의 법칙)

```
필요한 커넥션 수 = 초당 요청 수 × 요청 1건이 커넥션을 쥐는 시간(합)
→ 처리 한계(초당) = 풀 크기 ÷ (요청 1건이 커넥션을 쥐는 시간의 합)
```

| 단계 | 1건이 커넥션을 쥐는 시간 (측정값) | 계산한 한계 | 실측 최고 처리량 |
|---|---|---|---|
| 1 | 1회 × 18.6ms | 10 ÷ 18.6ms = **538/s** | 540/s |
| 2 | 1회 × 32.1ms | 20 ÷ 32.1ms = **623/s** | 620/s |
| 3 | order: 3회 × 7.2ms = 21.6ms / **delivery: 22.5ms** | order 463/s, **delivery 444/s** | 446/s |
| 4 | order: 3회 × 7.0ms = 21.0ms / **delivery: 21.4ms** | order 952/s, **delivery 467/s** | 469/s |
| 5 | **order: 3회 × 7.3ms = 21.9ms** / delivery: 13.5ms / hub: 3회 × 5.8ms | **order 457/s**, delivery 741/s, hub 575/s | 458/s |
| 6 | order: 3회 × 9.3ms = 27.9ms / delivery: 17.4ms / **hub: 3회 × 7.0ms = 21.0ms** | order 717/s, delivery 575/s, **hub 476/s** | 470/s |

- 점유 시간은 최고 부하 구간(45~100초)의 1초 단위 중앙값입니다.
- hub-ms는 주문 1건마다 3번 불립니다: order-ms의 재고 조회·차감, delivery-ms의 허브 경로 조회.
- **계산값과 실측이 모든 단계에서 3% 안으로 맞습니다.** 처리량은 요청 경로에서 가장 작은 풀이 정합니다.

### 3.2 언제부터 고갈되나 (1단계)

보정 측정(일정 부하 30초)으로 고갈 지점을 찾았습니다.

| 초당 주문 | 실패 | p95 | p99 | order-ms 풀 |
|---|---|---|---|---|
| 150 | 0% | 18.7ms | 22.8ms | 최대 3개 사용 |
| 300 | 0% | 17.8ms | 21.9ms | 최대 6개 사용 |
| 450 | 0% | 18.7ms | 33.5ms | 10개 모두 사용 (첫 보정에서는 대기 없음) |
| 600 | 0% | 937ms | 1,163ms | **고갈 28초**, 대기 190 |
| 800 | 0% | 5,269ms | 5,586ms | **고갈 35초 (전 구간)**, 처리는 약 575/s에서 막힘 |

스파이크 측정(1A)에서는 이렇게 진행됐습니다.
- **35초**: 부하가 약 540/s를 넘는 순간(급증 시작 5초 뒤)부터 커넥션 10개가 모두 사용 중이고 대기가 쌓이기 시작합니다.
- **35~116초 (81초 동안)**: 대기 190(= Tomcat 스레드 200 − 커넥션을 쥔 10)이 이어집니다. 최고 부하가 끝난 뒤에도 6초 동안 밀린 요청을 처리했습니다.
- **밀린 수요:** (800 − 540)/s × 60초 ≈ 1.56만 건이 처리되지 못하고 쌓였습니다. k6가 보내지도 못한 요청(1.44만 건)과 거의 같습니다.
- **커넥션 대기:** 중앙 357ms, 최대 4초였습니다. 대기 한도(30초)까지는 가지 않아 Hikari 타임아웃은 0건이었습니다.
  - 대기열이 커넥션 풀이 아니라 **그 앞(Tomcat 스레드 200, 그 뒤 TCP 접속 대기열)**에 쌓였기 때문입니다.
  - 사용자가 겪는 지연(p99 6.3초)의 대부분은 커넥션 대기가 아니라 스레드·접속 대기입니다.

### 3.3 풀을 얼마나 키울 수 있나 (2단계 20개 근거)

| 기준 | 계산 | 값 |
|---|---|---|
| 필요량 (리틀의 법칙) | 최고 800/s × 18.6ms ≈ 14.9 → 여유 1.3배 | **약 20** |
| DB 연결 상한 | `max_connections` 100 − 관리자 예약 3 − 다른 서비스 4×10 − 관리 접속 2 | order-ms가 더 쓸 수 있는 최대 약 55 |
| HikariCP 권장식 | DB 코어 15 × 2 + 디스크 1 ≈ 31 | **DB 전체**에서 동시에 일하는 연결 수의 기준. order 20 + 나머지 ≈ 60은 이미 넘음 |

- 인스턴스를 늘리면 DB 연결은 `인스턴스 수 × 풀 크기`로 늘어납니다. order-ms 3대 × 20 = 60이면 `max_connections` 100을 다른 서비스와 나눠 쓸 수 없습니다.
- 그래서 **"풀을 키운다"는 해법에는 DB 쪽 상한이 있습니다.** 스케일 아웃을 하려면 PgBouncer 같은 연결 풀러나 `max_connections` 조정이 같이 필요합니다.

## 6. 단계별 분석과 트레이드오프

### 1단계: 분리 전 + 풀 10 (기준)

- **무슨 일이 있었나**
  - 커넥션을 쥔 채 원격 호출 3번(재고 조회, 차감, 배송 생성)을 기다립니다.
  - 처리 한계 538/s를 넘자 커넥션 10개가 모두 사용 중이 됐고, 나머지 190개 스레드가 커넥션을 기다렸습니다.
- **장점**
  - 구조가 단순합니다. 실패하면 order DB가 한 번에 롤백됩니다.
  - **풀 10개가 하위 서비스로 가는 요청 수를 10개로 묶는 수문** 역할을 해서, hub와 delivery는 여유가 있었습니다(delivery 점유 8.2ms, 대기 0).
- **단점**
  - 하위 서비스가 느려지면(원격 대기 증가) 점유 시간이 그대로 늘어 한계가 더 떨어집니다. 예를 들어 delivery가 2초 타임아웃까지 가면 `10 ÷ 2초 = 초당 5건`이 됩니다.
  - 같은 풀과 스레드를 쓰는 조회도 함께 멈춥니다.

### 2단계: 분리 전 + 풀 20

- **무슨 일이 있었나**
  - 처리량은 540 → 620/s(+15%)로 조금 늘고, p50은 4.9초 → 2.3초로 줄었습니다.
  - 하지만 1건당 점유 시간이 18.6ms에서 **32.1ms로 늘었습니다.** 동시에 일하는 요청이 2배가 되자 원격 호출 대상(delivery 8.2 → 13.2ms)과 DB가 더 바빠졌기 때문입니다.
  - 풀이 2배여도 한계는 `20 ÷ 32.1ms ≈ 623/s`로 16%만 늘었습니다.
- **장점**
  - 설정값 하나라서 바로 적용할 수 있습니다. 네 단계 중 처리량과 성공 건수가 가장 좋았습니다.
- **단점**
  - **원격 대기를 커넥션으로 사는 방식이라 효율이 나쁩니다.** 커넥션 20개 중 대부분은 원격 응답을 기다리며 놀고 있습니다.
  - DB 연결 상한(3.3)과 인스턴스 수가 곱해져 금방 한계에 닿습니다.
  - 하위 서비스가 느려지는 장애에는 효과가 없습니다.

### 3단계: 분리 후 + 풀 10

- **무슨 일이 있었나**
  - 커넥션 1회 점유는 18.6ms에서 7.2ms로 줄었지만, **트랜잭션을 3번 열어서** 주문 1건이 쓰는 커넥션 시간의 합은 21.6ms로 오히려 늘었습니다.
    - 각 트랜잭션이 이력·주문을 다시 읽고 커밋하는 비용이 붙습니다.
    - 이 환경은 원격 호출이 노트북 안이라 빨라서(수 ms), 원격 대기가 줄어드는 이득보다 이 비용이 더 컸습니다.
  - **order-ms가 더 이상 수문 역할을 하지 않아,** 최대 200건이 동시에 delivery-ms로 몰렸습니다. delivery-ms 점유 시간이 8.2ms에서 22.5ms로 늘고, 그 풀(10)이 84초 동안 고갈됐습니다(대기 168).
  - 처리량은 delivery 한계(444/s)에 묶여 446/s로, 1단계보다 낮았습니다.
- **장점**
  - **원격 서비스가 느려져도 order-ms 커넥션은 묶이지 않습니다.** 하위 서비스 장애가 order DB 풀로 번지지 않습니다.
  - 같은 키의 동시 요청을 TX①에서 바로 거절하고 커넥션을 반납합니다.
- **단점**
  - 트랜잭션이 3번이라 정상 상황에서는 DB 일이 늘어납니다.
  - 중간에 서버가 죽으면 이력이 `IN_PROGRESS`로 남아서 복구 작업이 필요합니다.
  - **병목이 사라지지 않고 아래로 옮겨 갑니다.** 처리량을 올리려면 delivery-ms도 같은 방식으로 고쳐야 합니다.

### 4단계: 분리 후 + 풀 20

- **무슨 일이 있었나**
  - order-ms 풀은 한 번도 고갈되지 않았습니다(최대 16개 사용, 대기 0, 커넥션 대기 최대 14ms).
  - 처리량은 delivery 한계(467/s)에 묶여 469/s였습니다.
  - **조회 p99가 6.3초였습니다.** DB 풀은 비어 있었지만, order-ms의 **Tomcat 스레드 200개가 모두 delivery 응답을 기다리느라** 조회 요청이 스레드를 얻지 못했습니다.
- **장점**
  - order-ms 풀에 여유가 있어서 TX① 거절, 실패 기록, 조회 같은 짧은 작업이 커넥션 때문에 막히지 않습니다.
- **단점**
  - 하위 병목을 그대로 두면 풀을 키워도 처리량이 늘지 않습니다.
  - 공유 자원이 커넥션 풀에서 **스레드 풀**로 바뀌었을 뿐, 장애 전파는 그대로입니다.

### 5단계: order + delivery 분리 + 풀 10

- **무슨 일이 있었나**
  - delivery-ms 풀 대기가 168에서 0으로 사라졌습니다. 1회 점유도 22.5ms에서 13.5ms로 줄었습니다.
  - 대신 **order-ms 풀이 다시 막혔습니다**(고갈 81초, 대기 179, 커넥션 대기 중앙 124ms).
    - 분리 후 주문 1건은 트랜잭션 3번 × 7.3ms = 21.9ms를 씁니다. 풀 10으로는 `10 ÷ 21.9ms ≈ 457/s`가 한계이고, 실측 458/s와 같습니다.
    - 분리 전(1회 × 18.6ms)보다 커넥션 시간 합이 크므로, 풀이 같으면 분리 전보다 한계가 낮습니다.
- **장점**: 원격 대기가 order·delivery 어느 풀에도 묶이지 않습니다. 하위 장애 격리가 경로 전체에 적용됩니다.
- **단점**: 트랜잭션을 나눈 만큼 커넥션 시간 합이 늘어 **풀 크기 조정이 함께 필요합니다.** 그래서 6단계가 필요합니다.

### 6단계: order + delivery 분리 + 풀 20

- **무슨 일이 있었나**
  - order-ms 풀은 거의 고갈되지 않았고(7초, 대기 최대 16), delivery-ms도 대부분 여유가 있었습니다(대기 중앙 8).
  - 이번에는 **hub-ms 풀이 막혔습니다**(고갈 78초, 대기 중앙 151, Tomcat 사용 163).
    - hub-ms는 주문 1건마다 3번 불리고 1회 7.0ms를 씁니다. 풀 10으로는 `10 ÷ 21ms ≈ 476/s`가 한계이고, 실측 470/s와 같습니다.
  - 조회 p99는 6.1초로 여전히 느렸습니다. order-ms Tomcat 스레드 200개가 hub 응답을 기다렸기 때문입니다.
- **장점**: order·delivery 두 서비스가 더 이상 병목이 아닙니다. 다음 병목(hub)만 풀면 처리량이 오를 수 있는 상태가 됐습니다.
- **단점**: 서비스를 하나씩 고칠 때마다 다음 병목이 나옵니다. 경로 전체를 함께 계산해야 합니다(아래 "병목이 옮겨 가는 과정").

### 정리: 단계마다 무엇을 얻고 무엇을 치렀나

| 단계 | 얻은 것 | 치른 것 | 이런 경우에 맞음 |
|---|---|---|---|
| 1 | 단순함, 한 번에 롤백, 하위 서비스 보호(수문) | 처리 한계 538/s, 원격 지연이 그대로 풀 고갈로 | 트래픽이 한계보다 충분히 낮을 때 |
| 2 | 처리량 +15% (6개 중 최고), 설정만 바꾸면 됨 | DB 연결 2배, 원격 지연이 생기면 효과 없음, 인스턴스와 곱해짐 | 급한 임시 대응 |
| 3 | 원격 지연이 order 풀로 번지지 않음, 중복 요청 즉시 거절 | 트랜잭션 3번(DB 일 증가), 복구 작업 필요, 병목이 delivery로 이동 | 하위 서비스가 느리거나 불안정할 때 |
| 4 | 3의 장점 + order 풀 여유 | DB 연결 2배, delivery 병목 그대로 | 3에 하위 서비스 개선을 같이 할 때 |
| 5 | 경로 전체(order·delivery)의 원격 대기 격리 | 풀이 같으면 분리 전보다 한계가 낮음(457 < 538) | 풀 조정과 함께 쓸 때만 |
| 6 | order·delivery 병목 해소 | DB 연결 증가, hub가 다음 병목 | hub까지 함께 손볼 때 |

**이번 실험의 핵심 교훈**
- 처리량은 **요청 경로에서 가장 작은 풀**이 정합니다. 한 곳을 고치면 병목은 다음 곳으로 옮겨 갑니다(order → delivery → order → hub). 각 단계의 한계는 `풀 크기 ÷ (주문 1건당 그 서비스의 커넥션 시간 합)`으로 미리 계산할 수 있었습니다.
- 트랜잭션 분리의 이득은 **"빨라짐"이 아니라 "격리"**입니다.
  - 원격 호출이 수 ms인 이번 환경에서는 트랜잭션 횟수가 늘어난 비용이 더 커서, 같은 풀 크기에서는 오히려 한계가 낮았습니다(538 → 457).
  - 효과는 하위 서비스가 느려지는 장애 상황에서 나는데, 이번 측정에는 그 상황이 없었습니다(9장 다음 실험).
- 장애 전파를 막으려면 DB 풀뿐 아니라 **요청 스레드, 동시 실행 수, 입구 유입량**까지 같이 봐야 합니다. 6개 단계 모두 조회 p99가 5~7초였습니다.

## 7. 병목이 옮겨 가는 과정

```
1·2단계  [order 풀 ■■■■] → delivery → hub        order-ms가 원격 대기 동안 커넥션을 쥠
3·4단계  order → [delivery 풀 ■■■■] → hub        delivery-ms도 같은 구조 (원격 5번이 TX 안)
5단계    [order 풀 ■■■■] → delivery → hub        분리로 order 커넥션 시간 합이 늘어 풀 10 부족
6단계    order → delivery → [hub 풀 ■■■■]        주문 1건당 hub 3번 호출 × 7ms
```

**delivery-ms가 병목이었던 이유 (3·4단계)**

`DeliveryCommandService`에는 클래스 단위 `@Transactional`이 붙어 있어서, `createDelivery` 트랜잭션 안에서 원격 호출을 5번 합니다.

```
[TX 시작 → 커넥션 획득]
  companyClient.findCompany(공급업체)       원격
  companyClient.findCompany(요청업체)       원격
  hubRouteClient.getRouteEstimate(...)      원격
  userClient.pickDeliveryManagers(...)      원격
  userClient.getUserName(...)               원격
  deliveryRepository.save(배송 + 구간들)
[커밋 → 커넥션 반납]
```

order-ms가 동시 요청을 10건으로 묶어 줄 때(1·2단계)는 버텼지만, 묶음이 풀리자(3·4단계) 바로 고갈됐습니다. 5·6단계에서는 원격 조회를 트랜잭션 밖으로 빼서 이 병목을 없앴습니다(대기 168 → 0).

**hub-ms가 병목인 이유 (6단계)**
- 주문 1건마다 hub-ms를 3번 부릅니다: 재고 조회(order), 재고 차감(order), 허브 경로 조회(delivery).
- 1회 7ms × 3 = 21ms인데 풀은 기본 10이라서 한계가 476/s입니다.

**hub-ms 커넥션은 무엇을 기다렸나** (6단계 조건, 초당 800건, 1초 간격 20번 × 연결 약 10개 = 표본 188개)

| 상태 (`pg_stat_activity`) | 표본 | 비율 | 뜻 |
|---|---|---|---|
| 디스크 쓰기·읽기·WAL (`IO:DataFileWrite` 41, `IO:DataFileRead` 28, `LWLock:WALWrite` 23) | 92 | **약 49%** | 쓰기가 많은 차감 트랜잭션의 I/O, 작은 DB 캐시 |
| 실행 중 (대기 없음) | 35 | 19% | 쿼리 처리 |
| 트랜잭션 중 앱 대기 (`idle in transaction`) | 32 | 17% | 커넥션을 쥔 채 JVM이 다음 쿼리를 준비 |
| **행 잠금 대기** (`Lock:transactionid`) | 11 | **약 6%** | 재고 조건부 UPDATE의 동시성 제어 비용 |

- 실행 중이던 쿼리는 `COMMIT` 45, 재고 이력 INSERT 40, 재고 작업 INSERT 37, 멱등키 조회 31, 조건부 UPDATE 17, 경로 조회 2였습니다.
- **동시성 제어(행 잠금)는 약 6%로 작습니다.** 상품을 50개로 나눠 상품 하나당 초당 약 9건만 몰렸기 때문입니다. 잠금 방식을 바꿔도 줄어드는 몫은 이 정도입니다.
- 대부분은 차감 한 번이 테이블 3개(재고, 작업, 이력)에 쓰는 무거운 트랜잭션과 디스크 I/O입니다.
- hub-ms의 재고 차감은 이미 짧은 트랜잭션 구조(`TransactionTemplate`)라서, 풀 크기나 차감 트랜잭션 자체를 줄이는 쪽으로 풀어야 합니다.
  - **hub-ms 풀 조정**: 20으로 늘리면 계산상 약 950/s입니다. 코드 변경 없이 바로 확인할 수 있습니다.
  - **차감 트랜잭션 가볍게 하기**: hub 커넥션 시간의 대부분은 차감 트랜잭션입니다(아래 대기 분석). 쿼리 6번(멱등 조회, 조건부 UPDATE, 남은 수량 조회, 작업 INSERT, 이력 INSERT, COMMIT)을 줄이는 방법이 있습니다(8장 4번).
  - 허브 경로 캐시는 효과가 작습니다. 처음에는 "hub 호출 3번 → 2번이면 약 714/s"로 계산했지만, 이는 호출마다 커넥션 시간이 같다고 가정한 값입니다. 실제로 경로 조회는 대기 분석 표본 188개 중 2개뿐인 가벼운 쿼리라서, 빼도 줄어드는 시간이 작습니다.
  - **hub-ms 풀 조정**: 20으로 늘리면 계산상 약 950/s입니다.

**다른 공통 원인이 아닌지 확인**

3~6단계 처리량이 모두 446~470/s로 비슷해서, 서비스 풀이 아니라 공통 자원이 한계인지 따로 확인했습니다. 6단계 조건에서 초당 800건을 40초 보냈습니다.

| 확인 | 결과 | 판단 |
|---|---|---|
| DB CPU (`docker stats`) | 210% (15코어 중 약 2개분) | 여유 있음 |
| 초당 커밋 (`pg_stat_database`) | 약 5,200건 (주문 1건당 약 11건) | - |
| 커밋 디스크 동기화를 끔 (`synchronous_commit=off`, 측정 후 원복) | 처리 2.20만 → 2.29만 건 (+4%), hub 풀 대기 180 그대로 | 디스크 동기화는 주원인 아님 |
| 서비스별 풀 계산 (3.1) | 각 단계의 가장 작은 풀 한계와 실측이 3% 안 | **각 서비스의 풀이 원인** |

## 8. 다른 방법들과 트레이드오프

| # | 방법 | 막아 주는 것 | 비용·위험 | 이번 결과와의 관계 |
|---|---|---|---|---|
| 1 | **Hikari 풀 키우기** (2·4·6단계) | 풀 고갈을 늦춤 | DB 연결 상한, 인스턴스 수와 곱해짐, 원격 지연에는 무력 | 분리 전 +15%. 분리 후에는 꼭 같이 필요(5 → 6단계) |
| 2 | **트랜잭션 분리** (3~6단계) | 원격 지연이 DB 풀로 번지는 것 | 트랜잭션 횟수 증가, `IN_PROGRESS` 복구 필요, 병목 이동 | order 풀 고갈 81초 → 0초(4단계) |
| 3 | **하위 서비스도 트랜잭션 분리** (delivery-ms, 5·6단계) | 다음 병목 제거 | 영은님 코드 변경 | delivery 풀 대기 168 → 0 |
| 4 | **hub 차감 트랜잭션 가볍게 하기** (hub-ms, 이찬님 담당) | hub 커넥션 1회 점유 시간 | 재고 정합성에 직접 영향 → 충분한 테스트 필요 | 6단계 병목(hub)의 주원인. 아래 a~d |
| 5 | **벌크헤드: 기능별 동시 실행 제한** (세마포어, Resilience4j Bulkhead, 생성/조회 스레드 분리) | 생성이 스레드를 다 먹어 조회까지 멈추는 것 | 한도를 넘는 생성 요청은 바로 거절(429/503) → 재시도 안내 필요 | **조회 p99 5~7초(전 단계)를 막는 방법.** 예: 생성 동시 실행 100으로 제한하면 조회용 스레드 100이 남음 |
| 6 | **타임아웃 단축 + 서킷 브레이커** (Resilience4j) | 느린 하위 서비스를 오래 기다리는 것 | 오탐으로 정상 요청 실패, 결과를 모르는 요청 증가 → 보상·복구 로직 필요 | 하위 장애 때 스레드가 2초씩 묶이는 것을 줄임. 팀 합의로 지금은 안 씀(C03) |
| 7 | **입구에서 유입 제한: Gateway Rate Limiter** (Redis 토큰 버킷) | 처리 한계를 넘는 요청이 들어오는 것 자체 | 넘친 요청은 429로 거절, 한도는 측정으로 정해야 함 (이번 기준 약 450~540/s) | 블랙프라이데이의 기본 방어선. 들어온 요청은 빠르게 처리됨 |
| 8 | **대기열 (가상 대기실)** | 순간 폭주를 줄 세워 처리 한계 속도로 흘려보냄 | 별도 대기열 서비스·화면, 사용자는 기다림 | 1.5만~2만 건의 밀린 수요를 "이탈"이 아니라 "대기"로 바꿈 |
| 9 | **비동기 주문 접수** (202 + Outbox + 메시지 브로커, 사가) | 원격 호출과 요청 스레드·DB 트랜잭션의 결합 | Kafka 등 인프라, API 계약 변경(접수 후 상태 조회), 최종 일관성 | 요청 처리는 TX 1번(주문 접수)으로 끝나서, 순간 부하를 브로커가 흡수 |
| 10 | **Feign HTTP 클라이언트 커넥션 풀** (Apache HC5/OkHttp) | 서비스 사이 연결을 계속 새로 만드는 것 (포트 고갈) | 의존성 추가, 풀 크기 설정 | 이번 측정에서 초당 600건부터 포트가 고갈됨 (1장 보정) |
| 11 | **가상 스레드** (JDK 21, `spring.threads.virtual.enabled`) | Tomcat 스레드 200 한계 | DB 풀은 그대로라 대기만 커넥션 쪽으로 이동, 일부 라이브러리 고정(pinning) 주의 | 스레드가 병목일 때 조회를 살릴 수 있음. 단 생성의 유입 제한(5·7)이 같이 필요 |
| 12 | **읽기 분리** (조회 전용 풀·읽기 복제본·캐시) | 조회가 쓰기와 같은 자원을 두고 경쟁하는 것 | 복제 지연, 캐시 무효화, 인프라 | 상품 조회(P01)처럼 캐시하면 조회는 DB와 무관해짐. 단 스레드 공유는 5·11이 필요 |
| 13 | **스케일 아웃 + PgBouncer** | 인스턴스 1대의 스레드·풀 한계 | 인스턴스 × 풀 크기가 DB 연결 상한을 넘음 → 연결 풀러 필요, 비용 | 처리 한계가 대수에 비례해 늘어남. 단 hub 같은 하위 병목도 같이 늘려야 함 |

**4번: 차감 트랜잭션을 가볍게 하는 방법**

| 방법 | 내용 | 줄어드는 것 | 위험 |
|---|---|---|---|
| a. `UPDATE … RETURNING quantity` | 조건부 차감과 남은 수량 조회를 쿼리 하나로 (네이티브 쿼리) | 왕복 1번 | 작음 |
| b. 먼저 넣고 충돌로 판단 | 멱등 조회 없이 작업 INSERT를 먼저 하고, 멱등키가 겹치면 기존 결과 반환 (hub에 이미 있는 중복 처리 경로 활용) | 왕복 1번 | 처리 순서 변경 → 검증 필요 |
| c. 작업·이력 테이블 합치기 | 두 테이블이 거의 같은 정보를 두 번 저장 | INSERT 1번 + 인덱스 2개 | 설계 변경 (ERD·조회 API) |
| d. 시간순 UUID (UUIDv7 등) | 지금 PK는 무작위 UUID라 INSERT마다 인덱스의 아무 페이지나 건드림. 시간순이면 인덱스 끝에만 붙음 | 디스크 읽기·쓰기 대기 | 엔티티 ID 생성 방식 변경 |

허브 경로 캐시는 경로 조회가 가벼워서 효과가 작다고 판단해 표에서 뺐습니다(7장).

**추천 순서 (이 프로젝트 기준)**
1. **구조 정리**: 2·3번(order·delivery 트랜잭션 분리, 이번 실험 코드)과 1번(분리에 맞춘 풀 조정)을 **함께** 적용합니다. 하나만 하면 5단계처럼 오히려 한계가 낮아집니다. 이어서 hub-ms 풀 조정이나 4번(차감 트랜잭션 경량화)으로 hub 병목을 풉니다.
2. **블랙프라이데이 대비**: 7번(Gateway Rate Limiter)으로 처리 한계를 넘는 유입을 입구에서 자르고, 5번(벌크헤드)으로 조회를 보호합니다. 10번은 운영 전 필수입니다.
3. **다음 단계**: 6번(서킷 브레이커)과 9번(비동기 주문). 구조 변경이 크니 발표에서 개선 방향으로 소개합니다.

## 9. 한계와 다음 실험

- **원격 호출이 빠른 환경**
  - 모두 한 노트북이라 원격 호출이 수 ms입니다. 그래서 트랜잭션 분리의 이득(원격 대기 동안 커넥션 반납)이 작게 나왔습니다.
  - **다음 실험**: delivery-ms에 응답 지연(예: 300ms)이나 정지(`SIGSTOP`)를 주고 1단계와 5·6단계를 비교합니다. 예상은 1단계 order 풀 한계 `10 ÷ 0.3초 ≈ 33/s`로 붕괴, 분리 버전은 order 풀 영향 없음입니다.
- **측정 사이 데이터 누적 (가장 큰 한계)**
  - 측정마다 주문 약 5만 건이 쌓였는데 지우지 않았습니다.
  - 마지막에는 `p_delivery_routes` 161만 행(453MB), `p_inventory_operations`·`p_orders`·`p_order_histories`·`p_deliveries`·`p_inventory_histories`가 각 80만 행 안팎(200~300MB)이었습니다. DB 전체는 1.9GB입니다.
  - 1단계는 작은 테이블에서, 6단계는 큰 테이블에서 측정한 셈입니다. hub 1회 점유가 5.7ms(3단계)에서 7.0ms(6단계)로 늘어난 데에도 영향이 있었을 수 있습니다.
  - 그래서 **단계 사이의 작은 차이(수 %)는 의미를 두기 어렵습니다.** 병목이 어디로 옮겨 갔는지와 리틀의 법칙 계산은 각 측정 안에서 잰 값이라 영향을 받지 않습니다.
- **작은 DB 캐시 (`shared_buffers` 128MB, PostgreSQL 기본값)**
  - DB(1.9GB)보다 훨씬 작아서 캐시 적중률이 85.9%였습니다(보통 99% 이상이 정상).
  - 캐시에 없는 페이지를 디스크에서 읽고(`IO:DataFileRead`), 캐시가 꽉 차면 요청을 처리하던 연결이 직접 페이지를 써서 자리를 비웁니다(`IO:DataFileWrite`). hub 대기의 약 49%가 이것과 WAL 기록이었습니다.
  - 운영 DB는 보통 메모리의 25% 정도를 씁니다(컨테이너 8GB 기준 2GB). 이 값으로 바꾸면 모든 서비스의 커넥션 점유 시간이 짧아질 것으로 예상합니다.
- **다음 재측정 계획**
  - 측정마다 데이터를 비우고, `shared_buffers`를 2GB로 올린 뒤 1~6단계를 다시 잽니다.
  - 7단계(hub 풀 20)를 추가해 다음 병목이 무엇인지 확인합니다.
- **같은 CPU를 나눠 씀**: k6(가상 사용자 3,000), 서비스 7개, DB가 같은 CPU를 쓰므로 점유 시간에 CPU 경합이 섞여 있습니다. 1회 7ms 같은 점유 시간은 운영 환경보다 길 수 있습니다.
- **Hikari 대기 한도(30초)까지 가지 않음**: 대기열이 Tomcat과 접속 대기열에 쌓여 Hikari 타임아웃은 0건이었습니다. 대기 한도를 짧게(예: 3초) 바꾸면 "느림"이 "빠른 실패"로 바뀝니다. 이것도 선택지입니다.
- **측정 중 발견**
  - 측정 중 Gateway의 Redis 연결이 끊겨 `AUTH_UNAVAILABLE`(503)이 이어진 적이 있습니다. 재시작으로 복구했고, 원인은 확인하지 못했습니다.
  - PR #62의 테이블 이름 변경(`p_delivery` → `p_deliveries`) 뒤 로컬 DB에 옛 외래키가 남아 배송 생성이 실패했습니다. 옛 외래키를 지워 해결했습니다. 새 DB에서는 생기지 않는 문제입니다.

## 10. 재현

```bash
# 측정 PC 포트 (macOS, 재부팅하면 원래대로)
sudo sysctl -w net.inet.ip.portrange.first=10000 net.inet.tcp.msl=1000

sh ./gradlew bootJar
python3 perf/order-create/run.py seed                      # 업체 2, 상품 50(재고 각 1천만), 조회용 주문 1만
# 분리 전 코드로 빌드한 jar → before, 분리 후 → after
python3 perf/order-create/run.py jar before
python3 perf/order-create/run.py boot --jar before --pool 10
python3 perf/order-create/run.py probe --rates 450,600,800  # 고갈 지점 찾기
python3 perf/order-create/run.py run --id 1A --scenario A --peak 800 --base 200
python3 perf/order-create/run.py run --id 1B --scenario B --peak 800 --base 200 --read-rate 200
python3 perf/order-create/run.py boot --jar before --pool 20 --order-only   # 2단계
# ... 3·4단계는 --jar after
# 5·6단계: delivery-ms 분리 jar도 보관 후 --delivery after
python3 perf/order-create/run.py jar after --module delivery-ms
python3 perf/order-create/run.py boot --jar after --pool 10 --delivery after
python3 perf/order-create/run.py cleanup
```
