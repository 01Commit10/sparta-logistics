# 요구사항 정리

> 원본: Notion (3f72dc3e-f514-803b-b4a1-fe0331fc4b62)

PROCESS : 요구사항 -> 요구사항분석 → 기능정의 →도메인설계

### 3-1. 사용자 및 인증 도메인 — User/Auth Service 대진님 

| ID | 기능명 | 기능 정의 | 구분 |
|---|---|---|---|
| USR-01 | 회원가입 | 사용자 정보를 입력받아 계정을 생성하고 즉시 활성화 | 필수 |
| USR-02 | 로그인 | 사용자 ID와 비밀번호를 검증하고 JWT 발급 | 필수 |
| USR-03 | 사용자 조회 | 일반 사용자는 본인, 관리자는 전체 사용자 조회·검색 | 필수 |
| USR-04 | 사용자 관리 | 관리자가 사용자 정보를 생성·수정·논리적으로 삭제 | 필수 |
| USR-05 | 인증·인가 | Gateway에서 JWT와 사용자 역할을 검증 | 필수 |
| USR-06 | 배송담당자 식별 | User에 배송담당 여부(`is_delivery_manager`)를 저장해 식별하고, 배송 수정 시 배정된 담당자 ID와 인증 사용자 ID를 비교한다(MASTER 예외). 별도 배송담당자 서비스·엔티티는 두지 않는다. | 설계 결정 |

주요 비즈니스 규칙

회원가입 시 사용자 ID는 영문 소문자와 숫자로 구성된 4~10자, 비밀번호는 영문 대소문자·숫자·특수문자를 사용하는 8~15자 조건을 충족해야 합니다. 비밀번호는 BCrypt 같은 안전한 해시 알고리즘으로 저장합니다.

전역 역할은 `MASTER`, `USER` 두 단계입니다. 단, 로그인하지 않은 사용자도 회원가입과 로그인을 수행할 수 있도록 인증 예외 경로가 필요합니다.

### 3-2. 허브 및 재고 도메인 — Hub/Inventory Service 이찬님

| ID | 기능명 | 기능 정의 | 구분 |
|---|---|---|---|
| HUB-01 | 허브 조회 | 초기 등록된 17개 허브 정보 조회·검색 | 필수 |
| HUB-02 | 허브 간 경로 조회 | P2P 경로의 출발지, 도착지, 거리, 예상 소요시간 조회 | 필수 |
| HUB-03 | 재고 조회 | 특정 상품의 허브별 재고 수량 확인 | 필수 |
| HUB-04 | 재고 차감 | 주문 생성 과정에서 재고를 확인하고 주문 수량만큼 차감 | 필수 |
| HUB-05 | 재고 복원 | 주문 취소 또는 처리 실패 시 해당 재고를 복원 | 필수 |
| HUB-06 | 재고 등록·추가 | 개발 및 테스트에 필요한 초기 재고를 등록하거나 수량 추가 | 구현 방식 선택 |

주요 비즈니스 규칙

17개 허브와 P2P 경로는 초기 데이터를 적재한 후 조회 전용으로 운영합니다.

재고가 부족하면 주문은 실패해야 합니다. 동시에 여러 주문이 들어오는 경우에도 재고가 음수가 되지 않도록 동시성 제어가 필요합니다.

재고 추가는 입고 프로세스 전체를 구현하라는 의미는 아닙니다. 테스트 데이터를 초기 적재하는 방법도 가능합니다.

주요 비즈니스 규칙

하나의 업체는 생산업체와 수령업체 역할을 모두 수행할 수 있습니다.

상품은 별도 마이크로서비스가 아닌 Company/Product Service 내부에서 관리합니다. 공지 변경을 반영해 Company와 Product를 별도 엔티티로 두는 방향을 권장합니다.

다만 상품 CRUD의 개별 API 범위와 인가 규칙은 요구사항에서 완전히 확정된 것은 아니므로, 팀에서 구체화해야 합니다.

주요 비즈니스 규칙

주문이 정상적으로 생성되면 재고가 감소하고 배송 및 배송 경로 기록이 함께 생성되어야 합니다.

서로 다른 마이크로서비스의 데이터베이스 트랜잭션은 자동으로 함께 롤백되지 않으므로, 주문 서비스가 복구 절차를 조정하도록 설계하는 것이 적절합니다.

주요 비즈니스 규칙

배송 데이터와 배송 경로 기록은 주문 생성 시 함께 생성되어야 합니다.

배송담당자를 위한 별도 마이크로서비스나 엔티티는 만들지 않습니다.

배송 상태의 구체적인 종류, 상태 전이 규칙, 담당자 지정 방식은 팀이 정의해야 합니다. 거리 기반 자동 배차 최적화는 현재 필수 범위가 아닙니다.

**공통 감사 엔티티 설계 방향(권장)**

- 각 서비스의 JPA 엔티티는 `@MappedSuperclass`를 적용한 `BaseAuditEntity`를 상속하여 공통 감사 필드를 관리한다. 공통 클래스는 별도 테이블을 생성하지 않는다.
- `@EnableJpaAuditing`과 `AuditingEntityListener`를 활성화하고, `@CreatedDate`·`@LastModifiedDate`로 생성·수정 시각을 자동 기록한다. `@CreatedBy`·`@LastModifiedBy`에는 `AuditorAware`로 확인한 사용자 ID를 기록한다.
- `deleted_at`·`deleted_by`는 일반적인 JPA Auditing의 자동 기록 대상이 아니므로, `softDelete()`와 같은 명시적인 논리적 삭제 처리에서 기록한다. 일반 조회·검색은 `deleted_at IS NULL` 조건으로 삭제 데이터를 제외한다.
- MSA 환경에서는 Gateway의 인증을 통과한 사용자 ID를 각 서비스가 신뢰할 수 있는 방식으로 검증·전달받아 작업자를 기록해야 한다. 내부 시스템 작업의 기록 주체도 별도로 정한다.
- 공통 감사 구조는 서비스별로 적용하되 비즈니스 엔티티 자체를 서비스 간 공유하지 않는다. 구현 세부 코드와 삭제 데이터 조회 정책은 도메인 모델·공통 기술 설계에서 확정한다.
또한 PostgreSQL의 스키마 분리는 중요하지만, 다른 서비스의 스키마에 직접 접근하지 못하도록 계정 권한도 구분해야 실질적인 데이터 소유권을 유지할 수 있습니다.
