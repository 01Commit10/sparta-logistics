# 3. 도메인 모델

본 프로젝트는 B2B 물류 관리 시스템으로, 사용자 인증부터 업체·상품 관리, 허브별 재고 관리, 주문 및 배송 처리까지의 업무를 **5개의 독립적인 마이크로서비스**로 분리한다.

각 서비스는 명확한 비즈니스 책임과 데이터 소유권을 가지며, 서비스 내부에서는 엔티티 간 연관관계를 통해 데이터를 관리하고, 서비스 간에는 UUID 기반 참조와 API 통신을 활용한다.

재고 변경과 주문·배송 요청에는 멱등성 및 동시성 제어를 적용하여 중복 실행을 방지하고 데이터 정합성을 유지한다.

#### 1.인증 및 사용자 관리

사용자 계정과 접근 권한, 배송담당 여부 및 소속 조직을 관리한다.

### User

서비스를 이용하는 사용자를 나타내는 핵심 엔티티다. 로그인 정보, 사용자 권한, 배송담당 여부 및 소속 조직 정보를 관리한다.

사용자 권한은 `MASTER`, `USER`로 구분하며, 배송담당자 여부는 `isDeliveryManager` 속성으로 별도 관리한다. 따라서 일반 사용자에게도 배송 업무 권한을 부여할 수 있다. 배송담당자는 허브(`HUB`) 소속 사용자만 지정할 수 있다.

사용자는 업체(`COMPANY`) 또는 물류 허브(`HUB`)에 소속될 수 있다. 어느 곳에도 속하지 않는 본사 관리자는 본사(`HQ`)로 두며, `HQ`는 MASTER만 지정할 수 있다. 회원가입 시 소속 조직의 유형과 이름을 등록하고, 조직 확인이 완료되면 `organizationId`에 실제 조직의 UUID를 연결한다.

**핵심 규칙:** 사용자 권한과 조직 소속은 독립적으로 관리한다. 특정 조직에 소속되었다는 사실만으로 관리 권한이 부여되지는 않으며, 실제 권한은 사용자 역할과 업무별 인가 조건을 기준으로 검증한다.

계정은 두 경로로 생성된다. 비회원은 회원가입으로 `USER` 계정을 만들고, `MASTER`는 역할과 배송담당 여부를 지정해 계정을 만들 수 있다. 첫 `MASTER`는 Auth 서비스 기동 시 한 번 생성된다.

사용자 상태는 **활성**과 **삭제(탈퇴·비활성화)** 두 가지이며 `deletedAt`으로 구분한다. 삭제된 사용자는 로그인할 수 없고 `username`도 재사용할 수 없다. `MASTER`는 삭제된 사용자를 재활성화할 수 있다.

`MASTER`가 비밀번호를 초기화하면 `passwordChangeRequired`가 `true`가 되고, 사용자가 비밀번호를 바꿀 때까지 대부분의 기능이 제한된다.

**불변 조건:** 활성 `MASTER`는 항상 1명 이상이어야 한다. 활성 사용자 사이에서 `slackId`는 중복될 수 없다.

토큰 상태(Refresh Token, 로그아웃, 토큰 무효화)는 도메인 엔티티가 아니라 Redis에서 관리한다. → [[SYS-01 게이트웨이 인증 인가 설계]]

#### 2.물류 네트워크 및 재고 관리

전국 물류 허브의 구성과 허브 간 이동 경로를 관리하고, 각 허브에 보관된 상품의 재고 및 변경 이력을 관리한다.

### Hub

전국 물류 거점을 나타내는 엔티티로, 허브명과 주소를 관리한다.

사전에 정의된 17개 허브를 중심으로 물류 네트워크를 구성하며, 하나의 허브는 여러 업체를 관리하고 다양한 상품의 재고를 보관할 수 있다.

업체를 관리하는 허브와 상품이 실제 보관된 허브는 서로 다른 개념으로 구분한다.

### HubRoute

허브 간 이동 경로를 정의하며, 출발 허브, 도착 허브, 예상 이동 거리 및 소요시간을 관리한다.

17개 허브의 모든 방향 조합(272개)을 시드 데이터로 미리 등록하고 조회만 한다. 동일한 출발·도착 허브 조합은 UNIQUE 제약으로 하나만 존재한다. 경로에 방향성이 존재하므로 A→B와 B→A는 따로 관리한다.

### Inventory

특정 허브에 보관된 상품의 현재 재고를 관리한다.

하나의 허브와 상품 조합에는 하나의 재고 레코드만 존재하며, 재고 등록 시 초기 수량을 정하고 주문 처리 시 재고를 차감한다. 재고는 상품 소유 업체의 관리 허브에만 등록할 수 있다. 주문 실패나 주문 취소로 보상이 필요한 경우 기존 차감 수량을 복원한다.

재고 수량은 음수가 될 수 없으며(CHECK 제약), 동시 주문 상황에서도 정합성을 유지해야 한다. 기본 모드는 조건부 UPDATE로 차감하고, `redis-streams` 모드는 Redis Lua 스크립트로 먼저 차감한 뒤 Redis Stream으로 DB에 일괄 반영한다.

### InventoryMovement

재고 변경 내역을 기록하고 동일한 재고 작업의 중복 실행을 방지한다.

변경 유형은 입고(`INCREASE`), 차감(`DECREASE`), 복원(`RESTORE`)으로 구분하며, 변경 수량과 변경 후 재고, 관련 주문 UUID를 기록한다.

`idempotencyKey`를 통해 동일 작업의 중복 반영을 방지하고, 재고 수량 변경과 이력 저장을 하나의 로컬 트랜잭션에서 처리한다.

**핵심 규칙:** Inventory는 현재 재고의 정합성을 책임지고, InventoryMovement는 재고 변경의 추적성과 멱등성을 지원한다.

#### 3.업체 및 상품 관리

물류 거래에 참여하는 업체와 업체가 공급하는 상품 정보를 관리한다.

### Company

상품을 공급하거나 수령하는 업체를 나타내며, 업체명, 주소, 관리 허브 및 업체 관리자 정보를 관리한다.

각 업체는 하나의 관리 허브에 연결되며, 여러 상품을 등록할 수 있다. 업체 관리자는 `managerUserId`로 식별하고, 업체 정보 변경 시 실제 관리자 또는 해당 작업에 필요한 권한을 가진 사용자인지 확인한다.

### Product

업체가 공급하는 상품을 나타내며, 상품명, 설명, 단가 및 소속 업체 정보를 관리한다.

하나의 업체는 여러 상품을 소유할 수 있으며, 상품 단가는 음수가 될 수 없다.

상품 정보는 Company Service가 관리한다. Hub Service는 재고 관리를 위해 상품 UUID를 참조하고, Order Service는 주문 생성 시 상품 정보와 공급업체의 유효성을 확인한다.

**핵심 규칙:** 업체와 상품의 소유 관계를 명확히 유지하며, 다른 업체의 상품을 임의로 수정하거나 소유 관계에 맞지 않는 상품을 주문하지 못하도록 검증한다.

#### 4.주문 및 트랜잭션 관리

업체 간 상품 주문을 처리하고, 재고 차감과 배송 생성으로 이어지는 분산 비즈니스 흐름을 관리한다.

### Order

주문 요청 업체, 공급 업체, 상품, 주문 수량, 주문 당시 단가 및 총금액, 주문자와 주문 상태를 관리하는 핵심 엔티티다.

주문 생성 시 `PROCESSING` 상태로 시작하며, 재고 차감과 배송 생성이 완료되면 `COMPLETED` 상태로 변경한다. 처리 실패 시 `FAILED`, 취소가 확정되면 `CANCELED` 상태로 전환한다. 취소는 `COMPLETED` 상태의 주문만 할 수 있다.

주문은 업체와 상품 정보를 직접 소유하지 않고 UUID로 참조한다. 다만 주문 당시의 상품 단가는 `unitPriceSnapshot`에, 확정된 총금액은 `totalAmount`에 저장하여 이후 상품 가격이 변경되더라도 과거 주문 금액이 유지되도록 한다. 배송이 생성되면 반환된 `deliveryId`를 저장하여 주문과 배송을 연결한다. 재고 차감 작업 ID는 `stockOperationId`에 저장하고, 주문을 취소할 때 이 ID로 재고를 복원한다.

**핵심 규칙:** 주문 수량은 0보다 커야 하고, 주문 당시 단가와 총금액은 음수가 될 수 없다. 주문 상품은 공급 업체에 소속되어야 하며, 하나의 주문에는 최대 하나의 배송만 연결할 수 있다. 할인 및 배송비를 고려하지 않는 현재 설계에서는 `totalAmount = unitPriceSnapshot × quantity`로 계산한다.

### OrderHistory

주문 생성 요청의 처리 기록을 관리하고, 동일 요청이 반복 실행되는 것을 방지한다. 주문 취소는 각 단계(배송 취소, 재고 복원)가 멱등하므로 같은 요청을 다시 보내면 이어서 처리된다.

각 요청은 `operationType`과 `idempotencyKey` 조합으로 식별하며, 동일 키로 다른 내용이 전달되면 `requestHash`를 비교해 요청 충돌을 감지한다.

작업 상태는 `IN_PROGRESS`, `SUCCEEDED`, `FAILED`로 구분하고, 응답 코드와 마지막 오류를 함께 관리한다.

**핵심 규칙:** 일반적인 주문 상태 변경 이력이 아니라, API 요청 단위의 멱등성과 처리 결과를 관리하는 모델이다.

#### 5.배송 및 경로 관리

주문에 연결된 배송을 생성하고, 물류 허브 간 이동부터 최종 수취인까지의 배송 과정을 관리한다.

### Delivery

배송 대상 주문, 출발·도착 허브, 배송 주소, 수취인 및 배송담당자 정보를 관리하는 핵심 엔티티다.

하나의 주문에 하나의 배송만 생성되도록 `orderId`에 UNIQUE 제약조건을 적용한다.

수취인 이름만으로는 동명이인을 구별할 수 없으므로 `recipientUserId`로 식별한다. 수취인은 주문자이며 이 값은 필수다.

배송담당자는 구간(DeliveryRoute)마다 사용자 UUID로 지정하며, 배송담당자 여부(`isDeliveryManager`)를 검증한다. Delivery의 `deliveryManagerId`는 현재 구간의 담당자이며, `HUB_ARRIVED`가 되면 업체 배송 구간 담당자로 바뀐다.

### DeliveryRoute

하나의 배송을 구성하는 개별 이동 구간을 나타낸다.

허브 간 이동(`HUB_TO_HUB`)과 최종 업체 배송(`HUB_TO_COMPANY`)을 구분하며, `routeSequence`를 통해 이동 순서를 관리한다.

각 구간에는 출발·도착 허브, 예상 거리와 소요시간, 실제 이동 정보, 구간별 배송 상태 및 담당 배송기사를 기록한다.

배송은 최대 2개 구간으로 구성된다. 출발 허브와 도착 허브가 다르면 **출발 허브 → 도착 허브(`HUB_TO_HUB`) → 수령업체(`HUB_TO_COMPANY`)**, 같으면 `HUB_TO_COMPANY` 구간 하나만 만든다. 도착 허브는 수령 업체의 관리 허브다.

**핵심 규칙:** Delivery는 배송 전체 상태(`HUB_WAITING` → `HUB_MOVING` → `HUB_ARRIVED` → `DELIVERING` → `DELIVERED`, 취소 시 `CANCELED`)를, DeliveryRoute는 구간 상태(`WAITING` → `MOVING` → `ARRIVED`, 취소 시 `CANCELED`)를 관리한다. 출발 허브와 도착 허브가 같으면 `HUB_ARRIVED`에서 시작한다. 배송 취소는 아무 이동도 시작하지 않았을 때만 할 수 있다.

#### 6.도메인 관계와 트랜잭션 경계

각 서비스는 자신의 데이터를 소유하며, 비즈니스 규칙과 트랜잭션 일관성 요구사항을 기준으로 애그리거트(Aggregate)를 구성한다.

**User**는 사용자 권한과 소속 정보를 관리한다. **Inventory**는 재고 수량의 정합성을 책임지고 InventoryMovement와 함께 재고 변경을 처리한다. **Company**와 **Product**는 업체와 상품의 소유 관계를 관리한다.

**Order**는 주문 상태와 처리 흐름을 관리하며, **Delivery**는 배송 상태와 이동 구간을 관리한다. OrderHistory는 주문 작업의 멱등성을 지원하며, 배송은 `order_id` UNIQUE로 중복 생성을 막는다.

서비스 내부 관계에는 실제 외래키를 사용할 수 있지만, 서비스 간에는 UUID 기반 논리적 참조를 사용한다.

애그리거트의 경계는 단순한 엔티티 관계가 아니라, **하나의 트랜잭션에서 함께 일관성을 유지해야 하는 데이터의 범위**를 기준으로 결정한다.

#### 7.분산 트랜잭션 및 Saga

주문 생성 과정에서는 Order, Hub, Delivery 서비스가 협력한다.

### 정상 처리

**주문 요청 → 주문 생성 → 재고 차감 → 배송 생성 → 주문 완료**

Order Service는 상품과 공급 업체, 가격을 확인하고 재고가 충분한 허브를 고른 뒤 주문을 `PROCESSING` 상태로 저장한다. 이후 그 허브에 재고 차감을 요청하고, 차감에 성공하면 Delivery Service에 배송 생성을 요청한다.

배송이 생성되면 반환된 배송 UUID를 주문에 연결하고 `COMPLETED` 상태로 변경한다.

이때 주문의 완료는 재고 확보 및 배송 생성 절차가 완료되었다는 의미이며, 실제 배송 완료 여부는 Delivery Service에서 별도로 관리한다.

### 실패 및 보상 처리

재고 부족 또는 차감 실패가 발생하면 주문을 실패 처리한다.

재고 차감 이후 단계가 실패하면, 만든 배송은 취소하고 이미 차감한 재고는 복원하는 보상 트랜잭션을 수행한 뒤 주문을 `FAILED`로 바꾼다.

각 서비스는 자신의 로컬 트랜잭션만 처리하며, 서비스 간 작업의 전체 성공·실패 흐름은 Saga 패턴으로 관리한다.

네트워크 장애, 타임아웃, 응답 유실에 대비하여 재시도가 필요한 작업에는 멱등성 키를 적용한다. 이를 통해 이미 처리된 작업의 중복 실행을 방지하고 서비스 간 데이터 정합성을 유지한다.

#### 8.공통 설계 원칙

### 데이터 소유권

각 서비스는 자신의 도메인 데이터에 대한 생성·수정·삭제 책임을 가진다. 다른 서비스의 데이터를 직접 변경하지 않고 API를 통해 필요한 작업을 요청한다.

### 멱등성과 동시성

주문 생성, 배송 생성, 재고 변경 등 중복 실행이 위험한 작업은 멱등성 키와 UNIQUE 제약조건을 활용한다.

재고 변경에는 동시성 제어를 적용하고, 비즈니스 데이터 변경과 처리 기록을 적절한 로컬 트랜잭션으로 묶어 정합성을 확보한다.

### Audit 및 Soft Delete

모든 엔티티는 생성·수정·삭제 시각과 작업자 UUID를 관리한다.

Spring Data JPA Auditing과 공통 BaseEntity를 활용할 수 있으며, 데이터 보존이 필요한 삭제 작업에는 `deletedAt` 기반 Soft Delete를 적용한다.
