# 페이지네이션 사용법 (common.page)

> 작성: 권우 · 기준: `dev` b78d9c2 + `common/page-refactor` · 최종 수정: 2026-10-17
> 대상: 내 서비스에 **목록 조회 API**(page·size·sort)를 만드는 사람
> 요청·응답 규칙과 설계 이유는 [[SYS-08 페이지네이션 정렬 설계]]에 있습니다. 이 문서는 **따라 하기만** 합니다.

## 3줄 요약

1. Controller에서 `Pageable`을 받아 **`PagePolicy`로 정규화**하고, **`PageResponse`로 응답**합니다. size 범위(1~100, 밖이면 10)·정렬 허용 목록·기본 정렬(`createdAt DESC`)·보조 정렬(`id ASC`)이 자동으로 적용됩니다.
2. 서비스가 정할 것은 **정렬을 허용할 엔티티 필드**뿐입니다. `PagePolicy.of("name", "unitPrice")`
3. domain에서 Spring을 쓸 수 없는 서비스(ArchitectureTest로 막은 서비스)는 **`PageQuery`·`PageData`** 를 쓰고, 변환은 `SpringDataPages`에 맡깁니다.

## 1. 내 서비스는 어느 방식?

내 서비스 `ArchitectureTest`가 domain에서 `org.springframework..` 의존을 막는지 보고 고릅니다. 두 방식은 **같은 쿼리와 같은 응답**을 만듭니다 (common 테스트로 확인).

| 방식 | 언제 | 계층을 지나는 타입 | 현재 서비스 |
|---|---|---|---|
| **A. Spring 타입** | domain에서 Spring Data 타입을 허용 | `Pageable` → `Page` | ArchitectureTest에 해당 규칙이 없는 서비스 |
| **B. 순수 타입** | domain에서 `org.springframework..` 금지 | `PageQuery` → `PageData` | company-ms, user-ms |

> user-ms는 B 방식이 common에 생기기 전에 만들어져 자체 `PageQuery`·`PageData`(`com.user.domain.repository`)를 씁니다. 그대로 동작하며, common 타입으로 옮기는 것은 선택입니다.

## 2. 방식 B: 따라 만들기 (4개 파일)

예: company-ms 업체별 상품 목록 `GET /api/v1/companies/{companyId}/products`

```java
// ① presentation — Controller
/** 정렬 허용: 생성일(기본, 역순)·상품명·단가. size 1~100 밖이면 10 (07 서비스 정책 1.5) */
private static final PagePolicy PAGE_POLICY = PagePolicy.of("name", "unitPrice");

@GetMapping("/companies/{companyId}/products")
public PageResponse<ProductResponse> getProductsByCompany(@CurrentUser AuthUser authUser,
                                                          @PathVariable UUID companyId,
                                                          Pageable pageable) {
    PageQuery query = PAGE_POLICY.toQuery(pageable);                 // 정규화 + 순수 타입으로
    return PageResponse.from(productService.getProductsByCompany(companyId, query),
            query, ProductResponse::from);                            // 같은 query를 응답에 다시 씀
}

// ② application — Service: 변환 없이 받고 돌려준다
@Transactional(readOnly = true)
public PageData<ProductResult> getProductsByCompany(UUID companyId, PageQuery query) {
    findActiveCompany(companyId);                                     // 없는·삭제된 업체면 404
    return productRepository.findActiveByCompanyId(companyId, query).map(ProductResult::from);
}

// ③ domain — Repository 인터페이스 (import com.common.page.PageData / PageQuery)
PageData<Product> findActiveByCompanyId(UUID companyId, PageQuery query);

// ④ infrastructure — JPA 파생 쿼리 + 구현체
Page<Product> findByCompany_IdAndDeletedAtIsNull(UUID companyId, Pageable pageable);   // JpaRepository

@Override
public PageData<Product> findActiveByCompanyId(UUID companyId, PageQuery query) {
    return SpringDataPages.toPageData(
            jpa.findByCompany_IdAndDeletedAtIsNull(companyId, SpringDataPages.toPageable(query)));
}
```

끝입니다. 파생 쿼리는 내용 조회와 `count` 쿼리를 함께 실행하고, `DeletedAtIsNull` 조건이 두 쿼리 모두에 들어갑니다.

## 3. 방식 A: 따라 만들기

```java
// presentation - Controller
private static final PagePolicy PAGE_POLICY = PagePolicy.of("name");

@GetMapping
public PageResponse<XxxResponse> search(@ModelAttribute XxxSearchRequest request, Pageable pageable) {
    return PageResponsefrom(xxxService.search(reqeust.toCondition(), PAGE_POLICY.apply(pageable)),
            XxxResponse::from);
}

// application - Service
public Page<XxxResult> search(XxxCondition cond, Pageable pageable) {
    return xxxRepository.search(cond, pageable).map(XxxResult::from);
}

// domain:         Page<Xxx> search(XxxCondition cond, Pageable pageable);
// infrastructure: jpa.findAll(spec, pageable) 등 Pageable을 그대로 넘김
```

QueryDSL 정렬 변환, 별도 count 쿼리 주의점은 [[SYS-08 페이지네이션 정렬 설계]] 5장을 봅니다.

## 4. 클래스 한눈에

| 클래스 | 쓰는 곳 | 하는 일 |
|---|---|---|
| `PagePolicy` | presentation | `of(필드...)`로 API별 상수 생성. `apply()` → `Pageable`, `toQuery()` → `PageQuery` (규칙 동일) |
| `PageResponse<T>` | presentation | 응답 record. `from(Page, mapper)` (A) / `from(PageData, PageQuery, mapper)` (B) |
| `PageQuery` | 모든 계층 (B) | `page`, `size`, `orderList(PageOrder(property, ascending))`. `offset()` 제공. Spring 의존 없음 |
| `PageData<T>` | domain·application (B) | `content`, `totalElements`. `map()`은 content만 바꿈. Spring 의존 없음 |
| `SpringDataPages` | infrastructure (B) | `toPageable(PageQuery)`, `toPageData(Page)` |
| `SortOrder` | (응답 내부) | 응답 JSON의 정렬 한 건 `{property, direction}` |

## 5. 정렬 허용 필드 정하기

- **엔티티 필드명**을 씁니다. `unit_price`(컬럼명)가 아니라 `unitPrice`.
- `createdAt`은 넣지 않아도 항상 허용됩니다.
- 화면에서 실제로 정렬하는 필드만 넣습니다. 데이터가 많은 테이블이면 인덱스가 있는지 확인합니다.
- `PagePolicy`는 **API마다 상수**로 둡니다. 같은 서비스여도 API마다 허용 필드가 다를 수 있습니다.

## 6. 테스트하기

**Fake 저장소 (application 단위 테스트, 방식 B)** — 정렬은 무시하고 저장 순서대로 자릅니다. 정렬은 `@DataJpaTest`에서 확인합니다.

```java
@Override
public PageData<Product> findActiveByCompanyId(UUID companyId, PageQuery query) {
    List<Product> matched = store.values().stream()
            .filter(product -> product.getCompany().getId().equals(companyId))
            .filter(product -> !product.isDeleted())
            .toList();
    List<Product> content = matched.stream().skip(query.offset()).limit(query.size()).toList();
    return new PageData<>(content, matched.size());
}
```

**확인할 케이스**

| 계층 | 케이스 |
|---|---|
| presentation (`@WebMvcTest`) | 파라미터 없음 → `page=0`, `size=10`, `sort=[createdAt DESC, id ASC]` · `size=500` → 10 · 허용 밖 정렬 → 400 `INVALID_SORT_PROPERTY` |
| application (Fake) | 다른 소유자·삭제된 데이터 제외, 상위 리소스 없음 → 404, 범위 밖 page → 빈 content |
| infrastructure (`@DataJpaTest`) | 정렬 순서, `totalElements`가 삭제 제외 건수와 일치 |

**Postman** — 요청은 두 방식이 같습니다.

```
GET http://localhost:19090/api/v1/companies/{{companyId}}/products?page=0&size=10&sort=name,asc
Authorization: Bearer {{accessToken}}
```

## 7. 하지 말 것

- `PAGE_POLICY` 없이 `Pageable`을 Service에 바로 넘기지 않기. size 제한·정렬 검사·보조 정렬이 모두 빠집니다.
- `PageRequest.of(...)`를 Controller·Service에서 직접 만들지 않기. 같은 이유입니다.
- Spring `Page`(`PageImpl`)를 응답으로 그대로 반환하지 않기. 항상 `PageResponse`.
- (방식 B) domain·application에서 `PagePolicy`·`PageResponse`·`SpringDataPages`를 쓰지 않기. 이 셋은 Spring에 의존하지만 패키지가 `com.common.page`라 기존 ArchitectureTest가 잡지 못합니다. 아래 규칙 추가를 권합니다.

```java
@ArchTest
static final ArchRule 페이지_도구는_정해진_계층에서만_쓴다 =
        noClasses().that().resideInAnyPackage(DOMAIN, APPLICATION, INFRASTRUCTURE)
                .should().dependOnClassesThat().belongToAnyOf(PagePolicy.class, PageResponse.class);

@ArchTest
static final ArchRule SpringDataPages는_infrastructure에서만_쓴다 =
        noClasses().that().resideInAnyPackage(DOMAIN, APPLICATION, PRESENTATION)
                .should().dependOnClassesThat().belongToAnyOf(SpringDataPages.class);
```

## 8. 막히면

| 증상 | 확인 |
|---|---|
| 400 `INVALID_SORT_PROPERTY` | 그 필드를 `PagePolicy.of(...)`에 넣었는지. 응답 메시지에 허용 목록이 나옵니다 |
| 500 `PropertyReferenceException` | 허용 목록에 엔티티에 없는 이름(컬럼명·오타)을 넣음 |
| `size=500`을 보냈는데 500건이 옴 | Controller에서 `apply()`·`toQuery()`를 빠뜨림 |
| 페이지를 넘기면 같은 행이 또 나오거나 빠짐 | `PagePolicy`를 거치지 않아 `id` 보조 정렬이 없음 |
| `totalElements`가 실제와 다름 | 직접 작성한 count 쿼리에 `deleted_at IS NULL`이 빠짐 |
| ArchitectureTest 실패: domain → `org.springframework.data.domain` | 방식 B로 바꾸기 (`Pageable`·`Page` 대신 `PageQuery`·`PageData`) |
| 없는 상위 리소스인데 200 + 빈 목록 | Service에서 상위 리소스(업체 등) 존재 확인을 먼저 하기 |
