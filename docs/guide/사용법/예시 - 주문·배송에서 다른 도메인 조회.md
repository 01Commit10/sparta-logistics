# 예시: 주문·배송에서 다른 도메인 조회하기 (Feign)

> 작성: 대진 · 기준: `dev` d6af869 · 최종 수정: 2026-10-16
> 대상: 다울(order-ms), 영은(delivery-ms). 응답을 주는 쪽: 권우(company-ms), 이찬(hub-ms)
> 만드는 순서·계층 규칙은 [[예시 - 다른 서비스에서 사용자 조회]]와 같습니다. 이 문서는 **주문·배송에 실제로 필요한 조회 두 가지**를 같은 방식으로 풀어 씁니다.
> ✅ company-ms 내부 API(상품·업체 검증)는 **구현됐습니다**(2026-10-19 갱신, 1.2 계약은 실제 응답 기준).
> ⚠️ hub-ms의 **내부 API는 아직 없습니다.** 2부의 경로·응답 필드는 [[04 API 명세서]] Internal API 표를 바탕으로 한 **제안 계약**입니다. 이찬님과 확정한 뒤 이름만 맞춰 바꾸세요.
> ✅ 1.4·2.3의 코드(DTO·Feign 클라이언트·Adapter·검증기)와 3.1·3.2 테스트 11개를 dev 복사본에 **문서 그대로** 붙여 넣고 돌려 모두 통과를 확인했습니다(2026-10-16). 상대 서비스는 WireMock으로 대신했고, `OrderCreateFacade`(⑥)는 주문 구현에 따라 달라 실행하지 않았습니다.

## 0. 우리 프로젝트의 서비스 간 호출 전체 지도

| 부르는 쪽 | 받는 쪽 | 무엇 | 종류 | 언제 | 예시 문서 |
|---|---|---|---|---|---|
| order-ms | company-ms | 상품·업체 검증 (단가, 공급업체, 관리 허브) | **조회** | 주문 생성 ① | **이 문서 1부** |
| order-ms | hub-ms | 재고 차감·복원 | 변경 | 주문 생성 ②·보상 | [[Feign 호출 사용법]] 2·7장 |
| order-ms | delivery-ms | 배송 생성·취소 | 변경 | 주문 생성 ③·보상 | (Saga) [[02 장애 대응(Feign) 가이드]] 8장 |
| order-ms | user-ms | 주문자 slackId | **조회** | 주문 완료 알림 | [[예시 - 다른 서비스에서 사용자 조회]] 상황 B |
| delivery-ms | hub-ms | 허브 간 경로(거리·소요시간) | **조회** | 배송 생성 중 | **이 문서 2부** |
| delivery-ms | user-ms | 배송담당자인지 | **조회** | 담당자 배정 | [[예시 - 다른 서비스에서 사용자 조회]] 상황 A |
| company-ms | hub-ms | 허브 존재 확인 | 조회 | 업체 등록 | 2부와 같은 방식 |

- **조회**는 실패해도 되돌릴 것이 없습니다. "없음(404)"을 어떻게 다룰지와 "장애면 막을지 진행할지"만 정하면 됩니다.
- **변경**(재고 차감, 배송 생성)은 멱등성 키·보상까지 필요하므로 별도 문서를 봅니다.

## 1부. 주문 → 업체·상품 조회 (order-ms → company-ms)

### 1.1 왜 필요한가

주문 생성 요청에는 ID만 옵니다: 요청업체 ID, 공급업체 ID, 상품 ID, 수량. 주문을 만들려면 company-ms에서 다음을 알아내야 합니다([[07 서비스 정책]] 5.1).

| 확인할 것 | 어디서 | 쓰는 곳 |
|---|---|---|
| 상품이 있는가, **공급업체 소유인가** | 상품 조회 `companyId` | 검증 |
| 주문 시점 단가 | 상품 조회 `unitPrice` | `unit_price_snapshot`, `total_amount` |
| 공급업체·요청업체가 있는가 | 업체 조회 | 검증 |
| 출발·도착 허브 | 각 업체의 `hubId` | 배송 생성 요청(③)에 넘김 |
| 배송 주소 | 요청업체 `address` | 배송 생성 요청(③)의 `delivery_address` (SA 설계보완리포트 D-1) |
| 상품명·업체명 | 상품·업체 `name` | Slack 알림 스냅샷 |

### 1.2 계약 (구현됨)

```
GET /internal/v1/products/{productId}
200 → { "id": "…", "companyId": "…", "name": "생수 500ml", "unitPrice": 1200.00 }
404 → { "code": "PRODUCT_NOT_FOUND", "message": "…" }   // 없거나 삭제된 상품
404 → { "code": "COMPANY_NOT_FOUND", "message": "…" }   // 상품의 소속 업체가 삭제됨

GET /internal/v1/companies/{companyId}
200 → { "id": "…", "name": "A상사", "address": "서울시 …", "hubId": "…", "managerUserId": "…" }
404 → { "code": "COMPANY_NOT_FOUND", "message": "…" }   // 없거나 삭제된 업체
```

- 사용자 헤더(`X-User-*`) 없이 호출할 수 있습니다. 형식이 틀린 헤더를 보내면 401입니다.
- 상품 내부 조회는 상품 조회수를 올리지 않습니다.
- 아래 1.4 예제처럼 필요한 필드만 DTO에 두어도 됩니다(모르는 필드는 무시). 배송 주소가 필요하면 `CompanyResponse`에 `address`를 추가하세요.

### 1.4 코드

**① 응답 DTO (infrastructure)**: JSON 키와 이름을 똑같이

```java
public record ProductResponse(UUID id, UUID companyId, String name, BigDecimal unitPrice) {
}

public record CompanyResponse(UUID id, String name, UUID hubId) {
}
```

- 금액은 `BigDecimal`로 받습니다. `double`이면 `1200.10`이 `1200.0999…`가 될 수 있습니다.

**② Feign 클라이언트**: 한 서비스의 API는 한 클라이언트에

```java
@FeignClient(name = "company-ms")
public interface CompanyClient {

    @GetMapping("/internal/v1/products/{productId}")
    ProductResponse getProduct(@PathVariable("productId") UUID productId);

    @GetMapping("/internal/v1/companies/{companyId}")
    CompanyResponse getCompany(@PathVariable("companyId") UUID companyId);
}
```

**③ 도메인 값**

```java
public record ProductInfo(UUID id, UUID supplierCompanyId, String name, BigDecimal unitPrice) {
}

public record CompanyInfo(UUID id, String name, UUID hubId) {
}
```

**④ Port와 ④' Adapter**: 404는 empty로

```java
public interface CompanyPort {
    Optional<ProductInfo> findProduct(UUID productId);
    Optional<CompanyInfo> findCompany(UUID companyId);
}
```

```java
@Component
@RequiredArgsConstructor
public class CompanyAdapter implements CompanyPort {

    private static final String TARGET = "company-ms";
    private final CompanyClient companyClient;
    private final RemoteCallTemplate remote;

    @Override
    public Optional<ProductInfo> findProduct(UUID productId) {
        return notFoundAsEmpty("PRODUCT_NOT_FOUND", () -> {
            ProductResponse r = remote.executeWithRetryOnce(TARGET, () -> companyClient.getProduct(productId));
            return new ProductInfo(r.id(), r.companyId(), r.name(), r.unitPrice());
        });
    }

    @Override
    public Optional<CompanyInfo> findCompany(UUID companyId) {
        return notFoundAsEmpty("COMPANY_NOT_FOUND", () -> {
            CompanyResponse r = remote.executeWithRetryOnce(TARGET, () -> companyClient.getCompany(companyId));
            return new CompanyInfo(r.id(), r.name(), r.hubId());
        });
    }

    /** company-ms의 "없음" code만 empty로 바꾸고, 그 밖의 거절·장애는 그대로 던진다 */
    private static <T> Optional<T> notFoundAsEmpty(String notFoundCode, Supplier<T> call) {
        try {
            return Optional.of(call.get());
        } catch (RemoteBusinessException e) {
            if (notFoundCode.equals(e.getErrorCode().getCode())) {
                return Optional.empty();
            }
            throw e;
        }
    }
}
```

- 조회라서 `executeWithRetryOnce`(실패하면 즉시 1번 더)를 썼습니다. 일시적인 끊김에 강해지지만, company-ms가 느리면 한 호출이 최대 4초가 됩니다.
- company-ms의 오류 code는 common에 등록되지 않았으므로 **문자열로** 비교합니다. 등록되면 `==` 비교로 바꿔도 됩니다.

**⑤ 검증 규칙**: 조회 결과로 "주문 재료"를 만든다

```java
/** 검증을 통과한 주문 재료. 주문 저장·배송 생성·Slack 알림에 그대로 쓴다 */
public record OrderSource(ProductInfo product, CompanyInfo supplier, CompanyInfo requester) {

    public BigDecimal totalAmount(int quantity) {
        return product.unitPrice().multiply(BigDecimal.valueOf(quantity));
    }
}
```

```java
@Component
@RequiredArgsConstructor
public class OrderSourceReader {

    private final CompanyPort companyPort;

    public OrderSource read(UUID productId, UUID supplierCompanyId, UUID requesterCompanyId) {
        ProductInfo product = companyPort.findProduct(productId)
                .orElseThrow(() -> new BusinessException(OrderErrorCode.ORDER_PRODUCT_NOT_FOUND));
        if (!product.supplierCompanyId().equals(supplierCompanyId)) {
            throw new BusinessException(OrderErrorCode.PRODUCT_NOT_FROM_SUPPLIER);   // 남의 상품을 주문하려는 경우
        }
        CompanyInfo supplier = companyPort.findCompany(supplierCompanyId)
                .orElseThrow(() -> new BusinessException(OrderErrorCode.ORDER_COMPANY_NOT_FOUND));
        CompanyInfo requester = companyPort.findCompany(requesterCompanyId)
                .orElseThrow(() -> new BusinessException(OrderErrorCode.ORDER_COMPANY_NOT_FOUND));
        return new OrderSource(product, supplier, requester);
    }
}
```

- 상품을 먼저 조회합니다. 상품이 없거나 공급업체가 틀리면 업체 조회 두 번을 아낄 수 있습니다.
- `OrderErrorCode`는 예시입니다. 팀 규칙대로 common `com.common.exception`에 만들고 `ErrorCodeRegistry`에 등록합니다.

**⑥ 쓰는 곳**: 검증은 주문 저장(트랜잭션) **전에**

```java
@Service
@RequiredArgsConstructor
public class OrderCreateFacade {                     // @Transactional 없음

    private final OrderSourceReader sourceReader;
    private final OrderService orderService;         // 저장은 여기서 @Transactional

    public UUID create(CreateOrderCommand command) {
        OrderSource source = sourceReader.read(command.productId(), command.supplierCompanyId(), command.requesterCompanyId());
        UUID orderId = orderService.createProcessing(command, source.product().unitPrice(), source.totalAmount(command.quantity()));
        // 이후 ② 재고 차감 → ③ 배송 생성 (출발 허브 = source.supplier().hubId(), 도착 허브 = source.requester().hubId())
        return orderId;
    }
}
```

### 1.5 상황별로 무슨 일이 일어나나

| company-ms 응답 | 결과 | 클라이언트 응답 (제안) | 주문 저장 |
|---|---|---|---|
| 모두 200, 상품이 공급업체 소유 | `OrderSource` | 다음 단계로 | 저장 |
| 상품 404 | `ORDER_PRODUCT_NOT_FOUND` | 404 또는 400 | **안 함** |
| 상품의 `companyId` ≠ 공급업체 | `PRODUCT_NOT_FROM_SUPPLIER` | 400 | 안 함 |
| 업체 404 | `ORDER_COMPANY_NOT_FOUND` | 404 또는 400 | 안 함 |
| 500, 꺼짐, CB 차단 | `RemoteServiceException` | 503 | 안 함 |
| 응답 없음 (재시도까지) | `RemoteTimeoutException` | 504 | 안 함 |

- 검증을 저장 **전에** 하면 실패해도 되돌릴 것이 없습니다. [[SYS-13 장애 대응 설계]] 8.1 ①은 "주문 FAILED"로 적혀 있지만, 저장 전에 검증하면 FAILED 주문을 남길 필요 없이 바로 오류로 응답할 수 있습니다. **어느 쪽으로 할지는 다울님이 정합니다.**

## 2부. 배송 → 허브 경로 조회 (delivery-ms → hub-ms)

### 2.1 왜 필요한가

배송을 만들 때 구간(`p_delivery_routes`)을 함께 만듭니다([[07 서비스 정책]] 6.1). 허브는 모두 서로 직접 연결된 **P2P 모델**이라 구간은 이렇습니다.

| 경우 | 구간 | hub-ms 호출 |
|---|---|---|
| 출발 허브 ≠ 도착 허브 | ① `HUB_TO_HUB` (출발 허브 → 도착 허브) + ② `HUB_TO_COMPANY` (도착 허브 → 요청업체) | **①의 거리·소요시간을 조회** |
| 출발 허브 = 도착 허브 | `HUB_TO_COMPANY` 하나 | **부르지 않음** |

출발·도착 허브 ID는 order-ms가 배송 생성 요청에 넣어 줍니다(1부의 `supplier.hubId()`, `requester.hubId()`).

### 2.2 계약 (제안, 이찬님과 확정)

```
GET /internal/v1/hub-routes?departureHubId={id}&arrivalHubId={id}
200 → { "id": "…", "departureHubId": "…", "arrivalHubId": "…", "distanceKm": 325.50, "durationMin": 240 }
404 → { "code": "HUB_ROUTE_NOT_FOUND", "message": "…" }
```

- P2P라 출발·도착 한 쌍에 경로가 **하나**(`UNIQUE(from_hub_id, to_hub_id)`)이므로 목록이 아니라 객체 하나로 제안합니다. 목록으로 정해지면 `List<HubRouteResponse>`로 받고 첫 번째를 씁니다.

### 2.3 코드

**① 응답 DTO와 ② Feign 클라이언트**: 쿼리 파라미터는 `@RequestParam`

```java
public record HubRouteResponse(UUID id, UUID departureHubId, UUID arrivalHubId, BigDecimal distanceKm, int durationMin) {
}

@FeignClient(name = "hub-ms")
public interface HubRouteClient {

    @GetMapping("/internal/v1/hub-routes")
    HubRouteResponse findRoute(@RequestParam("departureHubId") UUID departureHubId,
                               @RequestParam("arrivalHubId") UUID arrivalHubId);
}
```

- `@RequestParam("…")` 이름을 꼭 적습니다. 빠뜨리면 파라미터가 본문으로 가거나 기동 오류가 납니다.
- 같은 서비스(hub-ms)를 부르는 클라이언트가 이미 있으면(예: 재고) 메서드를 그쪽에 추가해도 됩니다. **`@FeignClient(name = "hub-ms")`가 두 개면** 이름이 겹쳐 기동이 실패하므로, 나눠 두려면 `@FeignClient(name = "hub-ms", contextId = "hubRouteClient")`처럼 `contextId`를 다르게 줍니다. (실제로 확인: `contextId` 없이 두 개를 두면 기동 시 `BeanDefinitionOverrideException`)

**③ 도메인 값, ④ Port, ④' Adapter**

```java
public record HubRoute(UUID departureHubId, UUID arrivalHubId, BigDecimal distanceKm, int durationMin) {
}

public interface HubRoutePort {
    /** 경로가 없으면 empty. hub-ms 장애는 예외 */
    Optional<HubRoute> findRoute(UUID departureHubId, UUID arrivalHubId);
}
```

```java
@Component
@RequiredArgsConstructor
public class HubRouteAdapter implements HubRoutePort {

    private final HubRouteClient hubRouteClient;
    private final RemoteCallTemplate remote;

    @Override
    public Optional<HubRoute> findRoute(UUID departureHubId, UUID arrivalHubId) {
        try {
            HubRouteResponse r = remote.executeWithRetryOnce("hub-ms",
                    () -> hubRouteClient.findRoute(departureHubId, arrivalHubId));
            return Optional.of(new HubRoute(r.departureHubId(), r.arrivalHubId(), r.distanceKm(), r.durationMin()));
        } catch (RemoteBusinessException e) {
            if ("HUB_ROUTE_NOT_FOUND".equals(e.getErrorCode().getCode())) {
                return Optional.empty();
            }
            throw e;
        }
    }
}
```

**⑤ 구간 만들기**: 같은 허브면 부르지 않는다

```java
@Component
@RequiredArgsConstructor
public class DeliveryRoutePlanner {

    private final HubRoutePort hubRoutePort;

    /** 허브 간 구간. 같은 허브면 empty(허브→업체 구간만 만든다) */
    public Optional<HubRoute> hubToHubLeg(UUID departureHubId, UUID arrivalHubId) {
        if (departureHubId.equals(arrivalHubId)) {
            return Optional.empty();                                   // hub-ms를 부르지 않는다
        }
        HubRoute route = hubRoutePort.findRoute(departureHubId, arrivalHubId)
                .orElseThrow(() -> new BusinessException(DeliveryErrorCode.HUB_ROUTE_NOT_FOUND_FOR_DELIVERY));
        return Optional.of(route);
    }
}
```

- 이 조회도 **배송 저장 트랜잭션 전에** 합니다. 경로를 먼저 받고, 배송·구간 저장만 `@Transactional`로 묶습니다.

### 2.4 상황별로 무슨 일이 일어나나 (호출이 두 겹입니다)

배송 생성은 **order-ms가 부른 요청 안에서** 다시 hub-ms를 부릅니다(order → delivery → hub).

| hub-ms 응답 | delivery-ms | order-ms가 받는 것 | order-ms 처리 ([[02 장애 대응(Feign) 가이드]] 8장) |
|---|---|---|---|
| 200 | 배송·구간 저장, 201 | 성공 | 주문 COMPLETED |
| 404 경로 없음 | 4xx (`HUB_ROUTE_NOT_FOUND_FOR_DELIVERY`) | `RemoteBusinessException` | 재고 복원 → FAILED |
| 500, 꺼짐, CB 차단 | 503 (잡지 않으면) | `RemoteServiceException` | 재고 복원 → FAILED |
| 응답 없음 | 504 (잡지 않으면) | `RemoteServiceException` (상대가 5xx로 응답했으므로) | 재고 복원 → FAILED |

- order-ms의 배송 생성 읽기 타임아웃은 이 안쪽 호출(최대 2초 × 재시도 2번)보다 길어야 합니다. 그래서 [[SYS-13 장애 대응 설계]]가 order → delivery만 5초로 제안합니다([[Feign 호출 사용법]] 6장).
- delivery-ms가 hub-ms 오류를 잡지 않고 그대로 503·504로 응답하는 게 맞습니다. 배송을 만들지 못했으니, order-ms가 "처리 안 됨"으로 보고 보상하면 됩니다.

## 3. 테스트

### 3.1 검증 규칙: 가짜 Port (매 빌드, 가장 빠름)

```java
class OrderSourceReaderTest {
```

### 3.3 받는 쪽(권우·이찬)이 할 일

| 서비스 | 내부 API | MockMvc로 고정할 것 ([[05 통합 테스트 가이드]] 4.6) |
|---|---|---|
| company-ms ✅ | `GET /internal/v1/products/{id}`, `GET /internal/v1/companies/{id}` | 완료: 응답 필드 목록, 없거나 삭제되면 404 + 고유 code, 사용자 헤더 없이 동작 (`InternalProductControllerTest`·`InternalCompanyControllerTest`, 통합 테스트) |
| hub-ms | `GET /internal/v1/hub-routes?departureHubId=&arrivalHubId=` | 필드 이름(`distanceKm`, `durationMin`), 경로 없으면 404 + 고유 code, 같은 허브 쌍 요청 시 동작 |

양쪽이 완성되면 [[Feign 호출 사용법]] 7.3 방식(`@Tag("e2e")`)으로 실물끼리 한 번 맞춰 봅니다.
