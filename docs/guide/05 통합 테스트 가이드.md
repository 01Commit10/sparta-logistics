# 05. 통합 테스트 가이드

> 작성자: 대진 · 기준: `dev` d6af869 · 최종 수정: 2026-10-16
> 대상: 전원. 내 서비스 통합 테스트를 쓰는 사람과, 서비스를 모두 띄워 전체 흐름을 확인하는 사람
> 원칙: 이 문서의 설정·코드는 **이미 gateway-edge·user-ms·common 테스트에서 쓰고 있는 방식**입니다. 주문·재고·배송 API 경로와 DTO는 **예시**이니 각자 확정한 값으로 바꿔 주세요.

## 0. 요약

1. 통합 테스트는 **두 층**으로 나눕니다. ① 서비스 하나를 진짜 빈으로 띄우고 바깥(다른 서비스·Redis·Slack)만 가짜로 바꾸는 **서비스 통합 테스트**(JUnit, 자동). ② 모든 서비스를 실제로 띄우고 Gateway로 요청하는 **전체 통합 테스트**(Postman, 수동).
   - **쉽게 말해:** ①은 "내 서비스 안쪽 배선이 맞나"를 매번 빌드 때 확인하고, ②는 "다 같이 붙였을 때 진짜 되나"를 시연 전에 확인합니다.
2. 다른 서비스 호출은 **WireMock**으로 가짜 서버를 띄워 확인합니다. 정상, 4xx 거절, 5xx, 응답 지연(타임아웃), 연결 거부를 모두 만들 수 있어 **예외 3종별 처리**를 실제 Feign으로 검증할 수 있습니다.
   - **쉽게 말해:** 상대 서비스가 없어도, 상대가 "재고 없음", "서버 오류", "응답 없음"이라고 답하는 상황을 마음대로 연출할 수 있습니다.
3. 로그인 사용자는 테스트 요청에 **`X-User-Id`·`X-User-Role` 헤더 두 개**만 넣으면 됩니다. 토큰·Gateway는 필요 없습니다.
4. 전체 통합 테스트에서는 **장애 상황도 직접 만들어** 확인합니다. 서비스를 끄면 503, 멈추게 하면 504, Redis를 끄면 503 `AUTH_UNAVAILABLE`이 나와야 합니다.

## 1. 무엇을 어디서 테스트하나

| 층 | 도구 | Docker | 확인하는 것 | 예 (이미 있는 테스트) |
|---|---|---|---|---|
| 단위 | JUnit + Fake | ❌ | 도메인 규칙, Service·Facade 분기 | user-ms `fake/FakeTokenStore` 등 |
| 서비스 통합 (H2) | `@SpringBootTest` + MockMvc | ❌ | Controller→DB까지 실제 빈, 검증·오류 응답 형식, 권한 | `LoginIntegrationTest`, `MyAccountIntegrationTest` |
| DB 제약 (PostgreSQL) | Testcontainers | ✅ | UNIQUE·부분 UNIQUE·동시 요청, H2가 흉내 못 내는 SQL | `SignupPostgresTest`, `LastMasterWithdrawPostgresTest` |
| 서비스 간 호출 | `@SpringBootTest` + WireMock | ❌ | Feign 경로·DTO, 예외 3종별 처리, 보상 호출, 재시도 키 | common `FeignResilienceIntegrationTest` |
| 서비스 간 실물 계약 | `@SpringBootTest` + 진짜 Eureka·상대 서비스 (`@Tag("e2e")`, `-PincludeE2e`) | 상대 서비스 실행 | 내 Feign Adapter와 상대 서비스의 실제 경로·필드·오류 code가 맞는지 | [[Feign 호출 사용법]] 7.3 |
| 전체 (E2E) | 로컬 실행 + Postman | ✅ | Gateway 인증·라우팅, 실제 서비스 간 흐름, 장애 시나리오 | `docs/postman/…collection.json` (56개) |

- 위에서 아래로 갈수록 느리고 준비가 많습니다. **분기는 아래층(단위·서비스 통합)에서 촘촘히, 전체 테스트는 대표 시나리오만** 확인하세요.

## 2. 서비스 통합 테스트 기본 (H2)

### 2.1 이미 준비되어 있는 것

모든 `-ms`는 테스트 때 `test` 프로필로 돌고(루트 `build.gradle`), common의 `application-test.yaml`(testFixtures)이 자동으로 적용됩니다.

| 설정 | 값 | 의미 |
|---|---|---|
| DB | H2 메모리, `MODE=PostgreSQL`, `ddl-auto: create-drop` | Docker 없이 실행. 테스트 클래스(컨텍스트)마다 스키마 생성 |
| Eureka | `eureka.client.enabled: false` | Eureka 없이 실행 |
| 캐시 | `spring.cache.type: none` | Redis 캐시 대신 매번 실제 메서드 호출 |
| Redis 헬스 | 끔 | Redis 없이 컨텍스트 기동 |

### 2.2 기본 틀

```java
@SpringBootTest
@AutoConfigureMockMvc
class HubIntegrationTest {

    @Autowired MockMvc mockMvc;
    @Autowired JdbcTemplate jdbc;                         // DB 결과를 직접 확인할 때

    private static final String MASTER_ID = "00000000-0000-0000-0000-000000000001";

    @Test
    void MASTER는_허브를_수정한다() throws Exception {
        mockMvc.perform(patch("/api/v1/hubs/{id}", hubId)
                        .header(AuthContract.HEADER_USER_ID, MASTER_ID)       // 로그인 사용자 = 헤더 두 개
                        .header(AuthContract.HEADER_USER_ROLE, AuthRole.MASTER.name())
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                                { "name": "경기남부허브" }
                                """))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.name").value("경기남부허브"));

        assertThat(jdbc.queryForObject("select updated_by from hub.p_hubs where id = ?", String.class, hubId))
                .isEqualTo(MASTER_ID);                    // 감사 컬럼까지 확인
    }
}
```

### 2.3 API마다 최소한 확인할 것

| # | 케이스 | 기대 |
|---|---|---|
| ① | 정상 | 2xx, 응답 필드, DB 반영 (`created_by`·`updated_by` 포함) |
| ② | 사용자 헤더 없음 (로그인 필요 API) | 401 `UNAUTHENTICATED` |
| ③ | USER가 MASTER 기능 호출 | 403 `ACCESS_DENIED` (서비스의 `requireMaster()`) |
| ④ | 남의 데이터 (본인·소속 확인이 있는 API) | 403 |
| ⑤ | 입력 검증 실패 | 400 `INVALID_INPUT` + `errors[].field` |
| ⑥ | 없는 리소스 | 404 + 내 서비스 오류 code |
| ⑦ | 업무 규칙 위반 (중복·상태 전이 불가 등) | 409 등 + 내 서비스 오류 code |

- 오류 응답은 Gateway와 같은 공통 형식이라 `jsonPath("$.code")`로 확인합니다.
- `X-User-*` 헤더를 **하나만** 넣거나 형식이 틀리면 모든 API가 401입니다. 일부러 확인할 때 말고는 둘 다 넣으세요.

### 2.4 테스트끼리 데이터가 섞일 때

- 같은 테스트 클래스 안에서는 DB가 이어집니다. `@AfterEach`에서 `jdbc.update("delete from …")`로 지우거나, 테스트마다 다른 값(예: 무작위 username)을 쓰세요.
- 테스트 메서드에 `@Transactional`을 붙이면 끝나고 롤백되어 편하지만, **커밋 후 동작(AFTER_COMMIT 리스너, Slack 알림)은 실행되지 않습니다.** 그런 테스트에는 붙이지 마세요(5장).

## 3. PostgreSQL로 확인해야 할 때 (Testcontainers)

H2는 PostgreSQL을 완벽히 흉내 내지 못합니다. **부분 UNIQUE(`WHERE deleted_at IS NULL`), `::uuid` 같은 PostgreSQL 문법, 동시 요청 시 제약 위반, 잠금 조회**는 실제 PostgreSQL로 확인합니다.

```groovy
// 내 서비스 build.gradle
dependencies {
    testImplementation 'org.springframework.boot:spring-boot-testcontainers'
    testImplementation 'org.testcontainers:junit-jupiter'
    testImplementation 'org.testcontainers:postgresql'
}
tasks.named('test') {
    useJUnitPlatform {
        if (!project.hasProperty('includeContainer')) {
            excludeTags 'container'                     // 평소 빌드에서는 Docker 테스트 제외
        }
    }
}
```

```java
@Tag("container")
@Testcontainers
// 컨테이너가 컨텍스트보다 먼저 멈춰 create-drop의 종료 drop이 30초 걸리므로 create로 둔다
@SpringBootTest(properties = "spring.jpa.hibernate.ddl-auto=create")
@AutoConfigureMockMvc
class StockPostgresTest {

    @Container
    @ServiceConnection                                    // datasource 주소를 컨테이너로 자동 연결
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:18");
    ...
}
```

실행: `sh ./gradlew :hub-ms:test -PincludeContainer` (Docker Desktop이 켜져 있어야 합니다)

**동시 요청 테스트 요령** (`SignupPostgresTest` 방식): `ExecutorService`로 같은 요청 5개를 동시에 보내고 `CountDownLatch`로 출발을 맞춘 뒤, "성공 1개 + 나머지는 409"이고 **500이 하나도 없는지** 확인합니다. 재고 차감처럼 동시성이 중요한 API에 특히 필요합니다.

## 4. 다른 서비스 호출 테스트 (Feign + WireMock)

### 4.1 준비

```groovy
testImplementation 'org.wiremock:wiremock-standalone:3.9.2'
```

### 4.2 기본 틀

Eureka 대신 **가짜 서버 주소를 서비스 이름에 연결**합니다. `@FeignClient(name = "hub-ms")`는 그대로 두고, 테스트에서만 `hub-ms`가 WireMock을 가리키게 합니다.

```java
@SpringBootTest(properties = {
        "spring.cloud.openfeign.client.config.default.read-timeout=300",            // 타임아웃 테스트를 빠르게
        "resilience4j.circuitbreaker.configs.default.wait-duration-in-open-state=1s"})
@AutoConfigureMockMvc
class OrderCreateIntegrationTest {

    static final WireMockServer HUB = new WireMockServer(options().dynamicPort());
    static { HUB.start(); }

    @DynamicPropertySource
    static void services(DynamicPropertyRegistry registry) {
        registry.add("spring.cloud.discovery.client.simple.instances.hub-ms[0].uri",
                () -> "http://localhost:" + HUB.port());
    }

    @Autowired CircuitBreakerRegistry circuitBreakers;

    @AfterEach
    void reset() {
        HUB.resetAll();
        circuitBreakers.getAllCircuitBreakers().forEach(CircuitBreaker::reset);   // 앞 테스트의 실패 기록 지우기
    }

    @AfterAll
    static void stop() { HUB.stop(); }
}
```

- `@FeignClient`에 `url`을 넣어 WireMock을 가리키게 하지 마세요. 서비스가 기동하지 않습니다(`FeignClientUrlGuard`). 위처럼 **서비스 이름 → 주소** 연결만 바꿉니다.
- CB 상태는 컨텍스트에 남아 다음 테스트로 이어지므로 `@AfterEach`에서 초기화합니다.

> 테스트 클래스 전체 예시(정상·409·500·지연·CB·사용자 헤더 6개)는 [[Feign 호출 사용법]] 7.2에 있습니다.

### 4.3 상황 만들기 (예외 3종)

| 만들 상황 | WireMock 설정 | 내 코드가 받는 것 |
|---|---|---|
| 정상 | `aResponse().withStatus(200).withHeader("Content-Type", "application/json").withBody("{…}")` | 응답 DTO |
| 업무 거절 (재고 부족 등) | `withStatus(409).withBody("{\"code\":\"INSUFFICIENT_STOCK\",\"message\":\"재고가 부족합니다.\"}")` | `RemoteBusinessException`, `getErrorCode().getCode()`가 `INSUFFICIENT_STOCK` |
| 상대 서버 오류 | `withStatus(500)` | `RemoteServiceException` |
| 응답 없음 (결과 모름) | `withStatus(200).withFixedDelay(1000)` (read-timeout 300ms보다 길게) | `RemoteTimeoutException` |
| 상대가 꺼져 있음 | 아무도 안 듣는 포트를 서비스 주소로 등록 (`new ServerSocket(0)`으로 포트를 얻고 바로 닫기) | `RemoteServiceException` |
| CB 차단 | 500을 5번 이상 연속으로 받게 한 뒤 한 번 더 호출 | `RemoteServiceException` (요청이 WireMock에 **가지 않음**) |

```java
HUB.stubFor(post(urlPathEqualTo("/internal/v1/inventories/decrease"))
        .willReturn(aResponse().withStatus(409).withHeader("Content-Type", "application/json")
                .withBody("""
                        {"code":"INSUFFICIENT_STOCK","message":"재고가 부족합니다."}
                        """)));
```

### 4.4 상대에게 무엇을 보냈는지 확인 (`verify`)

```java
// 보상 호출이 정확히 1번 갔는지
HUB.verify(1, postRequestedFor(urlPathEqualTo("/internal/v1/inventories/restore")));

// 재시도(executeWithRetryOnce) 두 번 모두 같은 멱등성 키였는지
List<LoggedRequest> calls = HUB.findAll(postRequestedFor(urlPathEqualTo("/internal/v1/inventories/decrease")));
assertThat(calls).hasSize(2);
assertThat(calls).extracting(r -> r.getHeader("Idempotency-Key")).containsOnly(calls.get(0).getHeader("Idempotency-Key"));

// 사용자 헤더가 자동으로 이어졌는지
HUB.verify(postRequestedFor(anyUrl()).withHeader("X-User-Id", equalTo(USER_ID)).withHeader("X-User-Role", equalTo("USER")));
```

### 4.5 주문 Saga라면 (다울) 최소 시나리오

| # | WireMock 상황 | 기대 |
|---|---|---|
| ① | 업체·재고·배송 모두 정상 | 주문 `COMPLETED`, 재고 복원 호출 0번 |
| ② | 재고 409 `INSUFFICIENT_STOCK` | 주문 `FAILED`, 배송 호출 0번, 복원 호출 0번 |
| ③ | 재고 500 | 주문 `FAILED`, 복원 호출 0번 |
| ④ | 재고 응답 지연 | 같은 키로 재시도 → 그래도 지연이면 복원 호출 1번 + `FAILED` |
| ⑤ | 배송 409 / 500 | 재고 복원 호출 1번 + `FAILED` |
| ⑥ | 배송 응답 지연 | 배송 취소 + 재고 복원 + `FAILED` |
| ⑦ | 재고를 5번 넘게 500으로 | 이후 호출은 WireMock에 가지 않고 바로 `FAILED` (CB) |

- 단계별 처리 기준은 [[02 장애 대응(Feign) 가이드]] 8장, 확정은 다울님 몫입니다.

### 4.6 받는 쪽이라면 (이찬·영은·권우): 계약 테스트

다른 서비스가 Feign으로 부르는 **내부 API**는 MockMvc로 다음을 고정해 두세요. 호출하는 쪽 Feign DTO가 이 응답에 맞춰져 있습니다.

| # | 확인 |
|---|---|
| ① | 경로·메서드·응답 필드 이름과 타입 (필드 이름을 바꾸면 테스트가 깨지게) |
| ② | 사용자 헤더 **없이** 호출해도 동작 (스케줄러에서 온 호출에는 헤더가 없음) |
| ③ | 업무 거절은 공통 오류 형식 + 고유 `code`로 (`{"code":"INSUFFICIENT_STOCK", …}`) |
| ④ | 같은 `Idempotency-Key`로 두 번 오면 **처음 결과를 그대로** (재고가 두 번 줄지 않음) |

## 5. Slack 알림이 붙은 흐름 테스트

### 5.1 반드시: 진짜 발송 막기

테스트도 프로젝트 루트 `.env`를 읽습니다. `.env`에 `SLACK_WEBHOOK_URL`을 넣어 두었다면 **통합 테스트가 실제 Slack 채널로 보냅니다.** 둘 중 하나를 하세요.

```java
// 방법 1: 가짜 알림기를 빈으로 등록 (등록하면 common 자동 설정이 물러남). 보낸 내용을 확인할 수 있어 권장
@TestConfiguration
static class FakeSlack {
    @Bean RecordingSlackNotifier slackNotifier() { return new RecordingSlackNotifier(); }
}
```

```java
// 방법 2: 테스트 속성으로 끄기 (NoOp). 테스트 속성은 .env·yaml보다 우선합니다
@SpringBootTest(properties = "common.notification.slack.webhook-url=")
```

`RecordingSlackNotifier` 코드는 [[Slack 알림 사용법]] 5장에 있습니다.

### 5.2 커밋 후 알림 확인

> 단위 → 커밋 후 발송 → 진짜 발송기 + WireMock까지 단계별 전체 예시는 [[Slack 알림 사용법]] 5장에 있습니다.

- `@TransactionalEventListener(AFTER_COMMIT)`는 **실제로 커밋돼야** 실행됩니다. 테스트 메서드에 `@Transactional`을 붙이지 말고, API를 MockMvc로 호출해 서비스의 트랜잭션이 커밋되게 하세요.
- 확인할 것: 성공 → 알림 1번, 실패·롤백 → 0번, 이미 완료된 주문 재저장 → 추가 알림 없음, 메시지에 연락처·주소·요청사항 원문 없음.

## 6. 전체 통합 테스트 (모든 서비스 + Gateway)

### 6.1 띄우기

```bash
docker compose up -d postgres redis
sh ./gradlew :eureka-registry:bootRun        # 터미널 1
sh ./gradlew :user-ms:bootRun                # 터미널 2~6: 필요한 서비스
sh ./gradlew :hub-ms:bootRun
sh ./gradlew :company-ms:bootRun
sh ./gradlew :order-ms:bootRun
sh ./gradlew :delivery-ms:bootRun
sh ./gradlew :gateway-edge:bootRun           # 마지막
```

- http://localhost:8761 에서 모든 서비스가 `UP`인지 확인합니다. 기동 직후 몇 초는 Gateway가 아직 못 찾아 503일 수 있습니다.
- 자세한 준비(.env, 알려진 문제)는 [[로컬 실행·라우팅 확인 가이드]]를 보세요.

### 6.2 Postman으로 돌리기

1. 컬렉션 `docs/postman/sparta-logistics-gateway.postman_collection.json`을 가져와서 **Run collection**으로 한 번에 돌립니다. 지금 56개이며, 각 서비스 요청은 57번부터 이어 붙입니다.
2. 요청은 **모두 Gateway(`{{gateway}}`)로** 보냅니다. 토큰은 로그인 요청이 변수에 자동 저장합니다.
3. 6번 요청은 hub-ms가 **꺼져 있을 때만** 통과합니다. 모든 서비스를 띄웠다면 6번 실패는 정상입니다.

자세한 사용법과 내 요청 추가 방법은 [[Postman Gateway 테스트 가이드]] 5·7장에 있습니다.

### 6.3 시나리오 체크리스트

**인증·권한 (Gateway)**

| # | 시나리오 | 기대 |
|---|---|---|
| A1 | 토큰 없이 보호 API | 401 `TOKEN_MISSING` |
| A2 | USER 토큰으로 MASTER 전용 API (허브 수정, 업체 생성 등) | 403 `ACCESS_DENIED` |
| A3 | 로그아웃한 토큰으로 내 API | 401 `TOKEN_REVOKED` |
| A4 | 외부에서 `/internal/v1/...` 호출 | 404 |
| A5 | 응답 헤더 `X-Request-Id`로 Gateway 로그 한 줄 찾기 | `GET /api/v1/... 200 35 <requestId> <userId>` |

**업무 흐름 (예시, 각 담당자가 실제 API로 채움)**

| # | 시나리오 | 기대 |
|---|---|---|
| B1 | MASTER 로그인 → 허브·업체·상품 생성 | 각 201 |
| B2 | USER 가입·로그인 → 주문 생성 | 주문 성공, 재고 감소, 배송 생성 |
| B3 | 재고보다 많이 주문 | 주문 실패, 재고 그대로, 배송 없음 |
| B4 | 주문 완료 후 Slack | 개인 Webhook 채널에 1건 (`.env`에 URL 넣은 경우) |
| B5 | 주문 취소 | 재고 복원, 배송 취소 |
| B6 | 다른 사용자의 주문 조회 | 403 |

**장애 상황**

| # | 만드는 법 | 기대 |
|---|---|---|
| F1 | 서비스 하나(예: hub-ms) 터미널에서 Ctrl+C | 그 서비스로 가는 요청 503 `SERVICE_UNAVAILABLE`. **다른 서비스는 정상** |
| F2 | 서비스를 멈춘 채로 두기: `kill -STOP <pid>` (풀 때 `kill -CONT <pid>`) | 5초 뒤 504 `SERVICE_TIMEOUT` (주문 생성 경로는 15초) |
| F3 | F2 상태에서 같은 요청 5번 이상 | 이후 바로(수 ms) 503. Gateway가 그 서비스를 잠시 차단. `kill -CONT` 후 10초쯤 지나면 회복 |
| F4 | 주문 중 hub-ms만 멈춤 (F2) | (예시, 다울님 Saga 구현 기준) order-ms가 2초 뒤 `RemoteTimeoutException` → 주문 `FAILED` + 보상 |
| F5 | `docker compose stop redis` | 보호 API 전부 503 `AUTH_UNAVAILABLE`. 로그인도 503. `docker compose start redis` 후 회복 |
| F6 | Slack Webhook URL을 틀린 주소로 (`https://hooks.slack.com/services/x`) | 주문은 정상 완료, 서비스 로그에 WARN `Slack 알림 실패 … status=404` |

- `<pid>`는 `jps -l`로 찾습니다(예: `12345 com.hub.HubMsApplication`). `bootRun`이면 Gradle 데몬이 아니라 **애플리케이션 프로세스**의 pid여야 합니다.
- 서비스의 Feign Circuit Breaker 상태는 `curl -s localhost:19094/actuator/circuitbreakers`로 볼 수 있습니다. Gateway의 Circuit Breaker는 actuator로 노출하지 않습니다(GW-11 예정).

## 7. 실행 명령과 자주 막히는 것

```bash
sh ./gradlew :user-ms:test                      # 모듈별로 실행
sh ./gradlew :user-ms:test -PincludeContainer   # Docker 테스트까지
sh ./gradlew :user-ms:test --tests '*LoginIntegrationTest'   # 한 클래스만 (zsh에서는 따옴표 필요)
```

| 증상 | 원인 | 해결 |
|---|---|---|
| 루트 `sh ./gradlew test`에서 hub-ms `contextLoads` 실패 | H2에서 PostgreSQL 전용 시드(`db/seed/hubs.sql`)를 실행 | 모듈별로 실행. hub-ms는 테스트에서 `spring.sql.init.mode=never` (이찬님 확인 중) |
| 컨텍스트 기동 실패 `Feign 클라이언트에 고정 url이 있습니다` | 테스트용으로 `@FeignClient(url)`을 씀 | 4.2처럼 `simple.instances`로 주소 연결 |
| Feign 호출이 `RemoteServiceException`, 원인 `No instances available` | 테스트에 서비스 주소를 등록하지 않음 | `@DynamicPropertySource`에 `…instances.<서비스이름>[0].uri` |
| 앞 테스트 때문에 뒤 테스트가 503 | CB가 열린 채로 이어짐 | `@AfterEach`에서 `CircuitBreaker::reset` |
| AFTER_COMMIT 리스너가 테스트에서 안 돎 | 테스트 메서드에 `@Transactional` | 빼고 MockMvc로 API 호출 |
| 테스트 중 Slack에 메시지가 옴 | `.env`의 `SLACK_WEBHOOK_URL`을 테스트도 읽음 | 5.1 |
| 컨테이너 테스트 종료가 30초 멈춤 | `create-drop`이 멈춘 컨테이너에 drop 시도 | `ddl-auto=create` (3장) |
| `-PincludeContainer`인데 컨테이너 테스트가 안 돎 | 내 모듈 `build.gradle`에 태그 설정이 없음 | 3장의 `excludeTags` 블록 추가 |
