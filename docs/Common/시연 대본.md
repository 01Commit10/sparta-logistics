## 1. 회원·인증 (약 1분 30초)

> 말할 것: "인증은 Gateway가 한 번에 처리하고, 서비스는 Gateway가 넣어 준 사용자 헤더만 믿습니다."

| # | 명령 | 기대 결과 | 포인트 |
|---|---|---|---|
| 1-1 | `M=$(login <MASTER_USERNAME> '<MASTER_PASSWORD>')` | 토큰 저장 | `.env`의 MASTER는 user-ms 첫 기동 때 자동 생성 |
| 1-2 | 아래 "배송담당자 만들기" | 201, `isDeliveryManager: true`, `passwordChangeRequired: true` | MASTER가 만든 계정은 첫 로그인 후 비밀번호 변경 강제 |
| 1-3 | `D=$(login dm01 'Abcd123!'); curl -s $GW/api/v1/hubs -H "Authorization: Bearer $D" \| jq` | 403 `PASSWORD_CHANGE_REQUIRED` | 비밀번호를 바꾸기 전에는 내 정보·비밀번호 변경·로그아웃만 |
| 1-4 | 비밀번호 변경 후 다시 로그인 (아래) | 204 → 200 | 바꾸면 기존 토큰은 모두 무효 |
| 1-5 | `curl -s localhost:19095/internal/v1/users/$DM_ID \| jq` | `isDeliveryManager: true`, `slackId` | 배송 서비스가 Feign으로 보는 값 (서비스 포트로만, Gateway로는 404) |

```bash
# 1-2 배송담당자 만들기 (허브 소속만 가능)
DM_ID=$(curl -s -X POST $GW/api/v1/users -H "Authorization: Bearer $M" -H 'Content-Type: application/json' \
  -d '{"username":"dm01","password":"Abcd123!","name":"박배송","slackId":"<배송담당자 Slack 멤버 ID>","organizationType":"HUB","organizationName":"서울특별시 센터","role":"USER","isDeliveryManager":true}' | jq -r .id)

# 소속 허브 연결 (서울 허브 시드 UUID)
curl -s -X PATCH $GW/api/v1/users/$DM_ID/organization -H "Authorization: Bearer $M" -H 'Content-Type: application/json' \
  -d '{"organizationType":"HUB","organizationId":"10000000-0000-4000-8000-000000000001"}' | jq '{organizationType, organizationId}'

# 1-4 비밀번호 변경 → 다시 로그인
curl -s -o /dev/null -w '%{http_code}\n' -X PATCH $GW/api/v1/users/me/password -H "Authorization: Bearer $D" \
  -H 'Content-Type: application/json' -d '{"currentPassword":"Abcd123!","newPassword":"Newpw123!"}'
sleep 1; D=$(login dm01 'Newpw123!')
```

> 이미 `dm01`이 있으면(리허설 후) 409 `DUPLICATE_USERNAME`입니다. 리허설 때는 `dm02`처럼 바꾸거나, 이미 만든 계정으로 1-4부터 하세요.

## 2. Gateway 보안 (약 1분)

> 말할 것: "토큰 위조, 헤더 위조, 내부 API 직접 호출, 경로를 비틀어 우회하는 것을 Gateway 입구에서 막습니다."

| # | 명령 | 기대 결과 | 포인트 |
|---|---|---|---|
| 2-1 | `curl -s $GW/api/v1/users/me \| jq` | 401 `TOKEN_MISSING` | 공개 경로(가입·로그인·재발급·ID 확인) 외에는 토큰 필요 |
| 2-2 | `curl -s $GW/api/v1/users -H "Authorization: Bearer $D" \| jq` | 403 `ACCESS_DENIED` | MASTER 전용 경로 |
| 2-3 | 2-2에 `-H 'X-User-Role: MASTER'` 추가 | 403 그대로 | 외부에서 넣은 `X-User-*`는 지우고 토큰 값으로 다시 넣음 |
| 2-4 | `curl -s $GW/internal/v1/users/$DM_ID \| jq` | 404 `RESOURCE_NOT_FOUND` | 내부 API는 존재 자체를 숨김 (403이 아니라 404) |
| 2-5 | `curl -s "$GW/api/v1/users/%2e%2e/%2e%2e/internal/v1/users/x" -H "Authorization: Bearer $M" \| jq` | 400 `INVALID_INPUT` | 인코딩한 `..` 우회 차단 |
| 2-6 | `curl -si $GW/api/v1/users/me -H "Authorization: Bearer $D" -H 'X-Request-Id: demo-1' \| grep -i x-request-id` | `X-Request-Id: demo-1` | 요청 ID가 서비스 로그·응답까지 이어짐 |

## 4. 장애 대응 (약 2분) — 가장 중요

> 말할 것: "한 서비스가 죽거나 느려져도 Gateway가 빠르게 정해진 오류로 답하고, 다른 서비스는 계속 동작합니다. 인증 저장소(Redis)가 죽으면 안전하게 거부합니다."

| # | 하는 일 | 명령 | 기대 결과 (dev 실측) |
|---|---|---|---|
| 4-1 | user-ms **응답 지연** | `kill -STOP $(lsof -ti tcp:19095 -sTCP:LISTEN)` 후 로그인 | 정확히 **5초 뒤** 504 `SERVICE_TIMEOUT` |
| 4-2 | 지연 해제 | `kill -CONT $(lsof -ti tcp:19095 -sTCP:LISTEN)` | 바로 200 |
| 4-3 | user-ms **중지** | user-ms 터미널에서 `Ctrl+C` 후 로그인 | 즉시(수 ms) 503 `SERVICE_UNAVAILABLE` |
| 4-4 | 다른 서비스는 정상 | 이미 받은 `$M`으로 다른 서비스 API 호출 | 정상 응답 (Gateway는 JWT·Redis만 보고 user-ms를 부르지 않음) |
| 4-5 | 회로 열림 | 4-3 상태로 로그인 5~6번 → `curl -s localhost:19190/actuator/circuitbreakers \| jq '.circuitBreakers["user-ms"].state'` | `"OPEN"`, 이후 요청은 user-ms로 보내지 않고 바로 503 |
| 4-6 | 복구 | user-ms 다시 기동 | 약 15초 뒤 로그인 200, 회로 `HALF_OPEN` → `CLOSED` |
| 4-7 | **Redis 중지** | `docker stop sparta-logistics-redis` 후 `/users/me` | 503 `AUTH_UNAVAILABLE` (로그아웃한 토큰이 통과하지 않도록 거부) |
| 4-8 | 컨테이너는 안 죽음 | `curl $GW/livez` / `curl localhost:19190/actuator/health` | 200 `UP` / 503 `DOWN` (redis) — 헬스체크는 `/livez`라 재시작 반복 없음 |
| 4-9 | Redis 복구 | `docker start sparta-logistics-redis` | 몇 초 뒤 200 |

- **실수 주의**: 프로세스를 끌 때 `lsof -ti tcp:19095`처럼 `-sTCP:LISTEN` 없이 쓰면 연결된 **Gateway까지 같이 죽습니다.** 위 명령을 그대로 쓰세요.
- 주문 흐름의 장애(배송 서비스 중지 → 재고 복원 → 주문 FAILED)는 5장에서 다울·영은님이 보여 줍니다. Feign 쪽 분류(4xx 업무 거절 / 503 처리 안 됨 / 504 결과 모름)는 [[02 장애 대응(Feign) 가이드]] 4장.
