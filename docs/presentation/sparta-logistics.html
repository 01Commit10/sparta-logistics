요지

데이터 소유권은 스키마로 나누고, 빠른 상태 확인이 필요한 세 곳에 Redis를 썼다.

전환

목표를 봤으니, 그 목표를 위해 어떤 구조를 골랐는지.

핵심

  • 데이터는 서비스마다 스키마를 나눴고, 다른 서비스 데이터는 외래키 대신 ID만 들고 Feign으로 확인.
  • Kafka도 검토 — 보상·유실 방지에 강하지만 도메인마다 Producer·Consumer를 따로 구현해야 해서, 성능 개선 다음 목표로 잡았고 이번엔 시간 한계로 못 했다. 추후 개선 예정.
  • Redis는 사용자·허브·업체 세 서비스에: ① 사용자 — 로그아웃 토큰을 바로 막는 토큰 상태 ② 허브 — 재고, Lua 한 번으로 차감하고 Streams로 DB에 반영(10번에서 자세히) ③ 업체 — 상품 조회 캐시.

문제

TOP 10 초당 24건 · p99 2.5초, 검색 초당 19건 · p99 3.1초

원인

요청마다 DB가 100만 행 전체 스캔 — 정렬 + 전체 건수 count, 상세는 요청마다 조회수 UPDATE

① 인덱스  ② Redis 캐시  ③ Caffeine(L1) + Redis(L2) 2단

판단

인덱스는 count가 여전히 전체 스캔, 1~2글자 검색은 트라이그램 불가 → 2배 이하. DB에 가는 일 자체를 없앤다. Redis만이면 왕복·역직렬화가 남아 L1 추가 (대가: 서버 여러 대면 L1 옛 값 최대 10초)

전환

핵심

  • 상품 100만 건에 동시 50명이 30초 동안 쉬지 않고 조회. 처음엔 TOP 10이 초당 24건, p99 2.5초.
  • 인덱스부터 넣었는데 2배도 안 됐다 — 전체 개수를 세는 쿼리가 여전히 100만 건을 다 읽었기 때문.
  • 서버 메모리 Caffeine 10초 + 서버끼리 공유하는 Redis 5분·30초의 2단 구조로 초당 9만 건.

  • "7번 표의 S4 TOP 10은 95,656인데?" — 같은 레이어드 구성을 10/21에 다시 잰 값. 날짜가 달라 약 3% 차이, 흔들림 범위.

Q&A 대비

  • "DB 반영 전에 Redis가 죽으면?" — AOF always로 매 쓰기 fsync, 재시작 후 Pending 이벤트를 다시 읽어 반영. 데이터가 통째로 사라졌으면 시작을 멈추고 명시적 복구만.
  • noeviction은 docker-compose에 따로 쓰지 않음 — Redis 기본값이라 검사 통과.
  • "평소 트래픽에서도 빨라졌나?" — 아니다. 계단식(DS vs DS-pg)에서 hub 풀 고갈 371초 → 15초, hub 점유 4.82 → 2.62ms였지만 전체는 672 → 689 TPS(+3%, 흔들림 안). 병목이 order(338초)·delivery(83초)·company(92초) 풀로 옮겨 감. 효과는 "인기 상품에 몰릴 때"에 집중.

  • "운영 가능한가?" — 아직 두 가지 고쳐야 함: 기동 시 작업 기록 전체를 메모리로 읽어 37.5만 건에서 OOM(힙 512MB), Redis에 주문당 약 1.1KB가 지워지지 않고 쌓임(100만 주문 ≈ 1.1GB). 레포트 5장, hub 담당 공유됨.

전환

지금까지 고친 것을 한 표로 보면 이렇습니다.

핵심

  • 초당 주문을 400부터 100씩, 계단마다 60초. 처리량 98% 이상이고 p99 500ms 이하면 "버틴다".
  • 시작은 500 TPS에서 막혔고 700 TPS p99가 6.2초. 단계를 거쳐 800 TPS까지 버티고 700 TPS p99는 0.16초.
  • "먼저 막힌 풀" 열이 order → delivery → hub → order로 옮겨 다님 — 한 곳을 고치면 병목은 다음 서비스로 간다.

상호작용

"먼저 막힌 풀" 열을 위에서 아래로 손으로 따라간다.

Q&A 대비

  • "풀만 20으로 키우면?"(표에서 생략한 2단계: 버틴 최대 700~800, 초당 700건 p99 38~46ms) — 평소엔 맞다. 하지만 점유 시간이 그대로라 배송이 0.3초 느려지면 60 TPS로 무너짐(가운데 카드). 분리의 가치는 격리.
  • 풀만 키운 2·4·6·8·10단계는 표에서 생략(4: 700/736, 6: 700/786~798) — 둘 다 800 TPS 버팀, 최대 833·807. 경로 캐시를 고른 이유는 DB 커넥션을 늘리지 않아서.
  • 단계 3·5에서 버티는 TPS가 그대로인 이유 — 풀 10이라 다른 풀과 같이 막힘. 분리 효과는 같은 부하에서 커넥션 필요량(10.8 → 5.1개)으로 보임.
  • 800 TPS 근처는 노트북 한 대의 공통 한계. 절대값보다 비율과 막힌 위치를 본다. 반복 흔들림은 한 계단(100 TPS).
  • hub 경량화·경로 캐시는 실험 브랜치에만 있음(dev 미반영).
