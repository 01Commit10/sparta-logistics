### 슬라이드 1. 표지·프로젝트 소개: Sparta Logistics (0:30)

**핵심 메시지**: 허브 기반 B2B 물류 시스템 — 업체 간 주문을 받아 허브를 거쳐 배송까지 한 흐름으로 관리.

**화면**
- 제목: Sparta Logistics — 허브 기반 B2B 물류 MSA
- 한 줄 소개: **전국 17개 허브를 거점으로, 업체 간(B2B) 주문을 받아 허브를 거쳐 배송하는 물류 관리 시스템**
- 흐름 그림 (발제 예시, `docs/assets/d6c2dc3e-p2p_delivery_flow.svg` 참고)

```
[경기 공급 업체] ─ 상품 보관 ─ [경기 허브] ══ 허브 간 이동(P2P) ══> [부산 허브] ── 업체 배송 ──> [부산 수령 업체]
                                  ▲ 재고 차감                                        ▲ 배송담당자
        부산 수령 업체가 "마른오징어 50개" 주문 ────┘
```

- 핵심 개념 4개 (아이콘 + 한 줄)

| 개념 | 한 줄 |
|---|---|
| 허브 | 전국 17개, 지역 재고·물류 거점. 모든 허브가 서로 직접 연결(P2P) |
| 업체 | 특정 허브에 소속. 생산업체이자 수령업체 |
| 주문 | 주문하면 출발 허브 재고 차감, 재고 없으면 실패, 취소하면 복원 |
| 배송 | 주문마다 배송 1건 + 구간(허브→허브, 허브→업체), 배송담당자 자동 배정 |
| 사용자 | 회원가입·로그인(JWT), 권한 MASTER / USER, 배송담당자는 사용자 속성으로 지정 |

- 기간 10/13 ~ 10/21 · 서비스 5개(user, hub, company, order, delivery)

**대본**
> 안녕하세요, 저희 팀이 만든 Sparta Logistics는 전국 17개 허브를 거점으로 하는 B2B 물류 시스템입니다. 예를 들어 부산의 수산물 업체가 경기도 업체의 마른오징어를 주문하면, 경기 허브에서 재고를 빼고, 부산 허브로 옮긴 뒤, 배송담당자가 부산 업체까지 배송합니다. 이 주문부터 배송까지의 흐름을 서비스 다섯 개로 나눠, 다섯 명이 하나씩 맡아 구현했습니다.

출처: `docs/design/숙련프로젝트발제.md` 59~100행(시나리오·P2P 그림), README 1장

| 이름 | 담당 |
|---|---|

| 이찬 | 허브 · 경로 · 재고 |

**대본**
> 저희 팀은 이번 프로젝트를 **EDD, 이력서 드리븐 개발**이라는 목표로 시작했습니다. 이력서에 한 줄로 쓸 수 있는, 직접 부딪혀 보고 숫자로 증명한 경험을 만들자는 뜻입니다.

**화면 하단 이력서 한 줄 예**: 인기 상품에 주문 800 TPS 집중, **425 → 707 TPS (+66%)** · 행 락 대기 비중 79% → 0% · 재고 불일치 0건

### 슬라이드 3. 아키텍처 (1:00)

**화면**: README 4.1의 아키텍처 그림 (Client → Gateway → 서비스 5개, Eureka, Redis, PostgreSQL)

- 서비스 5개 + Gateway + Eureka, PostgreSQL 1대에 **서비스별 스키마 5개**
- 서비스 간 참조는 DB FK 없이 **UUID + Feign 내부 API**
- `/internal/**`는 Gateway에서 404로 숨김
- 각 서비스 4계층(presentation → application → domain ← infrastructure), ArchUnit으로 강제

**기술 선택 이유 (비교)**

| 고민 | 선택 | 이유 |
|---|---|---|
| DB 분리 수준 | DB 1대 + 스키마 분리 | 로컬·일정 제약 안에서 데이터 소유권은 지킴. 서비스별 DB 계정으로 남의 스키마 접근 차단 |
| 서비스 간 통신 | OpenFeign (동기), **Kafka는 미도입** | Kafka는 보상 처리·메시지 유실 방지에 강점이 있지만, 도메인마다 Producer·Consumer를 따로 구현해야 함. 성능 개선 다음 목표로 잡았으나 일정 한계로 진행하지 못함 → 추후 개선 예정 |
| 토큰 상태 저장 | **Redis** (refresh / blacklist / revoked-at 키, TTL) | 순수 Stateless JWT는 로그아웃·강제 무효화가 불가. DB 조회는 모든 요청마다 부담 → 메모리 조회 + 키마다 만료(TTL)가 맞음. Gateway가 요청당 MGET 1회로 확인 |
| 조회 캐시 | **Caffeine(L1) + Redis(L2)** 2단 캐시 | Caffeine만 쓰면 서버마다 캐시가 따로 놀고, Redis만 쓰면 매번 네트워크를 탐 → 둘을 겹쳐 빠르게 + 공유. 조회수도 Redis에 모았다가 주기적으로 DB 반영 |
| 재고 차감 | **Redis Lua + Redis Streams → DB 비동기 배치 반영** (`inventory.stock.mode=redis-streams`) | 고트래픽에서 재고 차감을 DB 행 락으로 처리하면 느려짐 → Lua 한 번으로 수량 검사·차감·작업 결과·Stream 이벤트 기록까지 원자적으로 처리하고 바로 응답. 전용 Consumer가 Stream을 읽어 최대 500건씩 재고·작업·이력·체크포인트를 한 트랜잭션으로 DB에 반영한 뒤 ACK → Redis에 남은 이벤트로 재전달·복구가 가능해 재고 데이터 유실을 막음 · 같은 코드에서 hub 모드만 바꿔 인기 상품 **425 → 707 TPS**, 행 락 대기 비중 79% → 0% |

- 상태: 부하 테스트 결과(인기 상품 행 락 상한 약 500 TPS)를 근거로 성능 개선, **dev 반영 (PR #80·#81, 10/21)**. 기본값은 Redis 모드(`redis-streams`)이고 설정으로 기존 PostgreSQL 모드 선택 가능
- 중복 반영 방지: DB에 어디까지 커밋했는지 체크포인트 테이블(`p_inventory_stream_checkpoints`)과 이벤트 해시로 확인 → ACK 실패로 재전달돼도 두 번 반영하지 않음
- 트레이드오프: Redis 모드의 200 응답은 **DB 반영 완료가 아님** (재고 조회 API는 Redis 수량을 보여 줌). Redis 미준비·과부하면 503
- TODO: Redis 모드 적용 전후 수치(인기 상품 집중 800 TPS)가 있으면 한 줄 추가
- 예상 질문 대비: "Redis 차감 후 DB 반영 전에 Redis가 죽으면?", "Redis와 DB 재고가 어긋나면 무엇을 기준으로 맞추나?"

**대본**
> 데이터는 서비스마다 스키마를 나눴고, 다른 서비스 데이터는 외래키 대신 ID만 들고 Feign으로 확인합니다.
> 서비스 간 통신에 Kafka도 검토했습니다. Kafka는 보상 처리나 메시지 유실 방지에 강점이 있지만, 도메인마다 Producer와 Consumer를 따로 구현해야 합니다. 그래서 성능 개선 이후의 다음 목표로 잡았는데, 시간 한계로 이번에는 진행하지 못했고 추후 개선할 예정입니다.
> Redis는 사용자, 허브, 업체 세 서비스에 썼습니다. 사용자 서비스는 로그아웃한 토큰을 바로 막기 위한 토큰 상태, 업체 서비스는 상품 조회 캐시, 허브 서비스는 재고입니다. 트래픽이 몰릴 때 재고 차감을 Lua 스크립트 한 번으로 Redis에서 처리해 바로 응답하고, 변경 내용은 Redis Streams에 이벤트로 남겨 전용 Consumer가 곧바로 묶어서 DB에 반영합니다. DB에 커밋한 뒤에만 이벤트를 지우기 때문에 중간에 실패해도 데이터가 유실되지 않습니다.

### 슬라이드 4. ERD·API 설계 (1:00)

### 슬라이드 5. 어려웠던 점과 해결: 학습 방식·블랙프라이데이 시나리오 (0:30)

**핵심 메시지**: "블랙프라이데이 오전 10시, 할인이 열리는 순간"을 가정하고, 트래픽이 몰리는 순서대로 어디서 병목이 생기는지 체크하고 고쳤다.

**학습 방식 (화면 상단)**
- 학습을 위해 **일부러 단순하게 구현한 출발점**에서 시작
  - 상품 조회: 캐시 없이 **DB만으로** 조회
  - 주문 생성: 재고 차감·배송 생성 원격 호출까지 **하나의 트랜잭션**으로 처리
- 이 상태에 **트래픽이 동시에 몰리는 상황을 k6로 재현** → 병목 지점을 측정으로 찾고 → 하나씩 해결 → 다시 측정

```
출발점 구현  →  트래픽 재현 (k6)  →  병목 측정  →  해결  →  재측정  ↺
```

**화면**: 시간 순서 띠 (장면 2개, 장면 2는 해결 3단계)

```
10:00 할인 오픈
  ├ 장면 1. 사람들이 상품을 찾는다        → 상품 조회 폭증                      (슬라이드 6)
  └ 장면 2. 사람들이 한꺼번에 주문한다     → 주문 생성 폭증, 병목이 옮겨 다님
       ├ ① 주문이 막힌다   → 주문 트랜잭션 분리                               (슬라이드 7)
       ├ ② 배송이 막힌다   → 배송 트랜잭션 분리                               (슬라이드 8)
       └ ③ 허브가 막힌다   → 재고 차감을 Redis로 분리                         (슬라이드 9)
```

- 각 장면을 **문제(어려웠던 점) → 원인 → 해결 → 결과** 순서로
- 측정: k6 부하 테스트, 노트북 1대 (절대값보다 **비율과 병목 위치**를 봄)
- 메모: 실제 측정은 상품 조회(10/19) → 주문 생성 단계별 개선 → 배송 지연·인기 상품 실험(10/20) → 허브 경로 캐시(10/21) 순서였음. 발표에서는 **사용자가 겪는 순서**(조회 → 주문)와 **dev에 반영한 해결 순서**(order → delivery → hub)로 재배치했고, 수치는 레포트 값 그대로

**대본**
> 저희는 학습을 위해 일부러 단순한 구현에서 출발했습니다. 상품 조회는 캐시 없이 DB만으로, 주문 생성은 재고 차감과 배송 생성까지 하나의 트랜잭션으로 구현했습니다. 그리고 이 상태에 트래픽이 동시에 몰리는 상황을 부하 테스트로 재현해, 병목 지점을 하나씩 찾아 해결하는 방식으로 이번 프로젝트에 임했습니다.
> 저희가 가정한 상황은 블랙프라이데이 오전 10시, 할인이 열리는 순간입니다. 사람들은 먼저 상품을 찾고, 이어서 한꺼번에 주문합니다. 이 순서대로 어디서 병목이 생기는지 체크하고 고친 과정을 말씀드리겠습니다.

### 슬라이드 6. 장면 1: 상품 조회가 몰린다 (0:50)

**부하 조건**: 상품 **100만 건**, k6 **동시 사용자(VU) 50명**이 응답을 받자마자 다음 요청을 보내며 **30초 동안 계속 조회** (워밍업 10초 별도). 동시 사용자를 10 → 50 → 100 → 200명으로 늘려 한 번 더 측정

**문제**: 할인 오픈과 동시에 인기 상품 TOP 10·검색이 몰림 → 동시 50명에서 TOP 10이 **초당 24건, p99 2.5초**, 검색은 **초당 19건, p99 3.1초**

| 단계 | 시도 | TOP 10 (req/s) | 검색 (req/s) | 결과 |
|---|---|---|---|---|
| 1 | 그대로 | 24 | 19 | 응답 2~3초 |
| 2 | **인덱스** 추가 | 51 | 20 | **2배도 안 됨** |
| 3 | Redis 캐시 | 39,586 | 19,540 | DB에 가는 일 자체를 없앰 |
| 4 | **Caffeine + Redis 2단 캐시** | **92,705** | **53,833** | p99 2.5초 → **1.4ms** |

- **원인 (인덱스가 안 통한 이유)**: 목록은 빨라졌지만 페이지의 전체 건수(count) 쿼리가 여전히 100만 행을 읽음. 1~2글자 검색어는 트라이그램 인덱스로 거를 수 없음

**2단(레이어드) 캐시에 무엇을 담았나**

| 저장 위치 | 담은 것 | 만료(TTL) | 역할 |
|---|---|---|---|
| **L1 Caffeine** (서버 메모리) | 상품 상세, 목록·검색·TOP 10 결과 페이지 (L2와 같은 데이터) | **10초**, 최대 1만 건 | 자주 찾는 값을 네트워크·역직렬화 없이 바로 응답 |
| **L2 Redis** (리모트) | 상품 상세 | **5분** (수정·삭제 시 삭제) | 서버 여러 대가 함께 쓰는 공유 캐시, L1이 비면 여기서 다시 채움 |
| | 목록·검색·TOP 10 결과 페이지 (검색어·페이지별 키) | **30초** (지우지 않고 만료로만 갱신) | |
| **Redis** (캐시 아님) | 상품별 조회수 누적 | 5초마다 DB 반영 | 조회마다 DB UPDATE → 5초에 한 번, UPDATE 11.4만 → 약 2.4만 번 |

- 읽기 순서: L1 → 없으면 L2 → 없으면 DB, 찾은 값은 위 단계에 다시 채움. 지울 때는 L2를 먼저 지움(L1을 먼저 지우면 그 사이 L2의 옛 값이 L1에 다시 들어올 수 있음)
- L1 효과: Redis만 쓸 때보다 1.5~2.8배. 검색 결과 페이지가 커서 검색에서 가장 큼(2.8배). Redis 조회가 118.8만 번 → 150번으로 줄어듦(L1이 만료될 때만 Redis를 봄)
- 대가: 서버가 여러 대면 다른 서버의 L1은 바로 안 지워져 최대 10초 옛 값

**동시 사용자를 늘리면 — 이름 검색 (2단 캐시)**

| 동시 사용자 | 10명 | 50명 | 100명 | 200명 |
|---|---|---|---|---|
| 캐시 없음 (req/s / p99) | 18 / 973ms | 19 / 3,090ms | 18 / 6,153ms | 17 / 12,040ms |
| 2단 캐시 (req/s / p99) | 44,005 / 0.3ms | **53,833 / 1.3ms** | 31,172 / 3.0ms | **278 / 18,510ms** |

- **남은 문제 (캐시 스탬피드)**: 200명에서 검색어별 캐시(30초)가 만료되는 순간 기다리던 요청이 한꺼번에 DB로 감 → 느린 검색 쿼리(약 400ms)가 커넥션 10개를 모두 잡고 대기 111명 → p99 18.5초

**측정에서 배운 것 → 개선 (`hot` 모드, dev PR #82)**

- 배운 것: 두 단에 **같은 데이터를 똑같이** 담으니 ① 키가 끝없이 늘어나는 검색 결과가 L1(최대 1만 건)을 채워 정작 자주 찾는 TOP 10·상세를 밀어내고 ② **비운 뒤 다시 담는** 순간(TTL 만료)마다 요청이 DB로 몰렸다
- 그래서 **데이터 성격에 따라 담을 곳을 나누고, 비우지 않고 덮어쓰는 갱신**으로 바꾼다

| 데이터 | 성격 | 담을 곳 | 갱신 |
|---|---|---|---|
| TOP 10 순위 (상품 ID) | 순위가 자주 바뀜, 모든 서버가 같은 순위를 봐야 함 | **Redis Sorted Set** | 조회할 때 점수 갱신 → 순위가 실시간 (100만 행 정렬·count 쿼리 없음) |
| TOP 10 상품 상세 | 수정이 드묾, 가장 많이 찾음, 10건뿐 | **Caffeine (L1)** | 스케줄러가 5초마다 새 목록을 만들어 **덮어씀** (비는 순간 없음) |
| 그 밖의 상품 상세 | 수정이 드묾, 조회가 흩어짐 | **Redis** (5분) | 수정·삭제 시 삭제 |
| 검색 결과 | 키 폭발, 재사용률 낮음 | **Redis만** (30초) | 같은 키는 한 요청만 DB를 읽음 (스탬피드 방지) |
| 조회수 | 쓰기 버퍼 | Redis | 5초마다 DB 반영 (기존과 같음) |

**개선 후 (같은 날 S4·S5 재측정, 상품 100만 건, 30초)**

| API · 동시 사용자 | S4 레이어드 (같은 데이터 두 단) | S5 hot (데이터별 분리) | 읽는 법 |
|---|---|---|---|
| TOP 10 · 50명 | 95,656 req/s, DB 전체 스캔 **22번** | 96,663 req/s, DB 전체 스캔 **0번** | 캐시가 비는 순간이 사라짐 |
| 검색 · 200명 | 7,861 req/s, 최대 지연 **19.5초** | **43,690 req/s**, 최대 지연 **1.1초**, 실패 0% | 스탬피드 해소 (5.6배) |
| 상세 · 50명 | 33,865 req/s | 24,817 req/s (−27%) | L1을 TOP 10으로 줄인 **대가** |
| 검색 · 50명 | 50,356 req/s | 34,214 req/s (−32%) | 검색을 L1에서 뺀 **대가** |

- 평균 처리량은 일부 줄었지만, **동시 사용자가 몰리는 순간 무너지지 않는 쪽**을 택함 (고트래픽 대비가 목표)
- 주의: S4 검색 200명은 첫 측정(278 req/s, p99 18.5초)과 재측정(7,861 req/s)이 다름 → 화면에는 **같은 날 재측정한 S4·S5 비교**만 씀. 같은 화면의 "남은 문제" 박스도 278 대신 "최대 19.5초 멈춤"으로 맞춤
- req/s 뜻: 가상 사용자가 응답을 받자마자 다음 요청을 보내는 방식(대기 없음)이라 **서버 최대 처리량**. 막힌 요청이 있으면 그 사용자가 멈춰 전체 처리량이 떨어짐
- 질문 대비 "S4가 한 건은 더 빠르지 않나?": 맞음. 중앙값 S4 1.1ms vs S5 3.8ms(L1 vs Redis). 평균 21.3 vs 4.5ms, 최대 19.5초 vs 1.1초 → 차이는 **만료 순간의 멈춤**. 그래서 말할 때는 "한 건이 빨라졌다"가 아니라 "몰리는 순간 멈추지 않는다"
- 질문 대비: S5 검색 50명에서 DB 전체 스캔 137번(5천만 행) — 단일 요청이 DB로 갈 때의 count 쿼리로 추정, 미확인
- 출처: `perf/product-query/results/p03/` (summary.md, `*-vu200.json`)

**대본**
> 첫 장면은 상품 조회입니다. 상품 100만 건에 동시 사용자 50명이 30초 동안 쉬지 않고 조회하게 했습니다. 인덱스부터 넣었는데 2배도 빨라지지 않았습니다. 전체 개수를 세는 쿼리가 여전히 100만 건을 다 읽고 있었기 때문입니다. 그래서 DB에 가는 일 자체를 없애는 캐시로 방향을 바꿨습니다. 서버 메모리의 Caffeine에는 10초짜리 짧은 캐시를, Redis에는 서버끼리 공유하는 5분·30초 캐시를 두는 2단 구조로 초당 24건을 9만 건까지 올렸습니다. 다만 동시 사용자 200명에서는 검색 캐시가 만료되는 순간 요청이 한꺼번에 DB로 몰려 초당 278건으로 무너졌습니다.
> 측정해 보니 두 단에 같은 데이터를 똑같이 담은 게 문제였습니다. 그래서 데이터 성격에 따라 나눴습니다. 순위가 자주 바뀌는 TOP 10 순위는 모든 서버가 함께 보는 Redis에, 거의 바뀌지 않는 TOP 10 상품 상세는 서버 메모리의 Caffeine에 두고, 캐시를 비웠다 다시 담는 대신 스케줄러가 새 값으로 덮어써서 캐시가 비는 순간을 없앴습니다. 그 결과 동시 사용자 200명의 검색이 초당 7,800건에서 4만 3천 건으로 올라갔고, 최대 지연도 19초에서 1초로 줄었습니다. 대신 평소 상세·검색 처리량은 조금 줄었는데, 몰리는 순간에 무너지지 않는 쪽을 택했습니다.

### 슬라이드 7. 장면 2-①: 주문이 몰린다 → 주문 트랜잭션 분리 (1:00)

**문제**: 초당 주문을 400부터 100씩 올리자 **500 TPS에서 order DB 커넥션 풀 고갈이 시작**되고, **600 TPS에서 p99가 500ms를 넘음** (고갈이 사용자가 느끼기 약 100 TPS 전에 먼저 나타남)

**원인**: **주문 생성 로직이 하나의 트랜잭션으로 구성** — 주문 DB 저장이 같은 트랜잭션에 있어, 재고(hub)·배송(delivery) Feign 호출을 기다리는 동안에도 **DB 커넥션 풀을 점유**

**해결**: 원격 호출은 트랜잭션 밖, DB 작업만 짧은 트랜잭션(멱등키 선점 → 주문 저장 → 확정/실패 기록) — dev PR #78 (Facade + TxService)

**결과**

| | 분리 전 | 분리 후 |
|---|---|---|
| 600 TPS에서 order 커넥션 필요량 | 10.8개 | **5.1개 (−53%)** |
| 배송이 300ms 느려질 때 최대 처리 | **60 TPS** (p99 56초) | **581 TPS (9.7배)** |
| order 커넥션 1회 점유 (배송 지연 시) | 333ms | 1.6ms |

- 진짜 가치는 "빨라짐"보다 **격리**: 하위 서비스가 느려져도 우리 DB 풀까지 번지지 않음
- 대가: 평소 응답 p50 +5ms (트랜잭션 3번)
- **그런데 → 이번엔 delivery 풀이 고갈** (다음 슬라이드)

**질문 대비 (화면에는 안 넣음)**
- "풀만 키우면 되지 않나?" → 평소에는 풀 10 → 20만으로 500 → 700~800 TPS였음. 분리 후에도 최대치는 노트북 한 대 한계(약 800)에 걸림. 분리의 가치는 같은 부하에서 커넥션 절반 + 하위 지연 시 격리(60 → 581)
- 실험 측정은 `TransactionTemplate` 방식, dev는 같은 원리를 Facade + TxService로 구현

**대본**
> 두 번째 장면은 주문입니다. 초당 500건에서 주문 서비스의 DB 커넥션이 바닥나기 시작했습니다. 주문이 트랜잭션 안에서 재고와 배송 서비스를 부르면서 커넥션을 쥔 채 응답을 기다린 게 원인이었습니다. 그래서 원격 호출을 트랜잭션 밖으로 뺐고, 같은 부하에서 커넥션을 절반만 쓰게 됐습니다. 효과가 가장 컸던 건 배송 서비스가 0.3초 느려졌을 때입니다. 분리 전에는 초당 60건으로 무너졌고, 분리 후에는 581건을 처리했습니다. 그런데 이번에는 배송 서비스의 커넥션이 막혔습니다.

### 슬라이드 8. 장면 2-②: 이번엔 배송이 막힌다 → 배송 트랜잭션 분리 (0:25)

### 슬라이드 9. 장면 2-③: 이번엔 허브가 막힌다 → 재고 차감을 Redis로 분리 (0:25)

**문제**: 병목이 **hub 풀**로 옮겨 감 (dev DB 방식: 600 TPS부터, 계단 전체 371초 고갈). 인기 상품 하나에 800 TPS가 몰리면 **425 TPS, p99 7.4초, hub DB 대기의 79%가 행 락** (상품당 약 500 TPS가 DB 방식의 상한)

**원인**: 주문 1건이 hub DB를 **3번** 부름 (재고 조회·재고 차감·경로 조회) + 같은 상품의 재고 한 줄을 모든 주문이 차례로 잠금

**해결**: 재고 **차감**을 **Redis Lua**로 처리하고, DB에는 **Redis Streams**로 비동기 반영 — dev PR #80·#81 (`inventory.stock.mode=redis-streams`, 기본값)

| 단계 | 하는 일 (소스 기준) |
|---|---|
| ① 차감 요청 | `reserve.lua` 한 번으로 멱등 키 확인 → 수량 검사 → Redis 재고 차감 → `XADD`로 이벤트 기록 → **DB를 거치지 않고 바로 응답** (행 락 없음) |
| ② DB 반영 | Consumer 스레드 1개가 Stream에서 **최대 500건**을 읽어 작업·재고·이력·체크포인트(`p_inventory_stream_checkpoints`)를 **한 트랜잭션**으로 저장 |
| ③ 확인 | DB 커밋이 끝난 뒤에만 `XACK`. 실패하면 Pending에 남아 재처리, 체크포인트의 순번(sequence)으로 중복 반영을 막음 |
| ④ 조회 | 재고 목록은 DB에서, **수량은 Redis 값**으로 덮어 응답 (DB 반영 전에도 최신 수량) |
| ⑤ 보상 | 주문 실패 시 재고 복원도 같은 Lua로 처리 (원 차감 작업 ID 기준, 중복 복원 거부) |

**유실·과부하 대비 (소스에 있는 장치)**
- Redis 설정 검사: `appendonly yes` + `appendfsync always` + `noeviction`이 아니면 재고 모드가 **요청을 받지 않음** (PR #81, docker-compose에 반영)
- 밀린 이벤트가 **1만 건 이상**이거나 가장 오래된 미반영 이벤트가 **10초 이상**이면 차감을 **503으로 거절** → DB가 못 따라오면 Redis가 무한정 앞서 나가지 않음
- 운영 중 Redis 데이터가 사라지면 오래된 DB 값으로 자동 복구하지 않고 **시작을 멈춤** (명시적 복구만 허용)
- 트레이드오프: 200 응답 = Redis 차감 완료이지 **DB 커밋 완료가 아님** (반영 지연은 Consumer 지표 `inventory.stream.persistence`로 확인)

**배운 것 (장면 2 전체)**
- 한 서비스만 고치면 병목은 다음 서비스로 옮겨 간다 (order → delivery → hub)

DB 커밋 뒤에만 이벤트를 확인 처리하고, 반영이 10초 넘게 밀리면 차감을 거절합니다. 같은 코드에서 허브 모드만 바꿔 다시 쟀더니 707 TPS, 행 락 0%, Redis와 DB 불일치 0건이었습니다. 이렇게 병목이 order에서 delivery, hub로 옮겨 다니는 것을 측정으로 확인하면서 하나씩 고쳤습니다.
