# SA 설계 보완 리포트

> 작성일: 2026-10-13
> 검토 대상: [[SA 설계 문서]] (00~07)
> 기준 문서: [[숙련 프로젝트 발제]], [[요구사항 정리]]

## 요약

검토 결과 **39건**의 보완점을 찾았습니다. 도메인 모델·멱등성·Saga처럼 MSA의 핵심 고민은 잘 드러나 있습니다. 반면 **주문 → 재고 → 배송으로 이어지는 흐름의 구체 규칙**(어느 허브에서 차감하고 어떤 경로로 보내는지)이 비어 있고, 발제·요구사항과 **API 범위가 어긋나는 곳**이 여러 군데 있습니다.

| 우선순위 | 의미 | 건수 |
|---|---|---|
| 🔴 높음 | 구현 전에 반드시 정해야 함. 정하지 않으면 서비스 간 구현이 어긋남 | 9 |
| 🟡 중간 | 발제 요구 누락 또는 문서 간 불일치. SA 피드백 전에 정리 권장 | 18 |
| 🟢 낮음 | 품질·가독성 개선 | 12 |

### 가장 먼저 처리할 5가지

1. **재고 차감 허브와 배송 출발·도착 허브를 정하는 규칙** 정의 → **D-1**
2. **P2P 모델과 다구간 배송 예시의 모순** 해소 → **D-2**
3. **Spring Boot 버전**: 발제는 3.x 지정, 설계는 4.1.1 → **T-1**
4. **누락된 API** 추가: 주문 삭제, 배송 삭제, 관리자 사용자 생성 → **A-2**
5. **테이블 명세 정리**: `p_orders` 중복, `p_inventory_movements` 누락 → **E-1**

## 01. 기술스택

| ID | 우선 | 보완점 | 제안 |
|---|---|---|---|
| T-1 | 🔴 | **발제는 "Spring Boot 3.x"를 지정**했는데 설계는 Spring Boot **4.1.1** | 튜터에게 4.x 사용 가능 여부 확인. 불가하면 3.x로 변경 |
| T-2 | 🔴 | **Spring Cloud release train 버전이 없음**. Boot와 Cloud 버전이 맞지 않으면 Gateway·Eureka·OpenFeign이 기동되지 않음 | Boot 버전에 맞는 Spring Cloud 버전을 명시하고 BOM으로 관리 |
| T-3 | 🟡 | 요구사항 SYS-14(Swagger·OpenAPI, 권장)가 스택에 없음 | `springdoc-openapi` 추가. Gateway에서 서비스별 문서를 묶을지도 결정 |
| T-4 | 🟢 | "Resilience4j"만 적혀 있음 | `spring-cloud-starter-circuitbreaker-resilience4j`처럼 Feign 연동 방식을 명시 |
| T-5 | 🟢 | 테스트가 JUnit·Mockito·Postman뿐. Saga·동시성은 실제 DB가 필요 | 통합 테스트용 Testcontainers(PostgreSQL) 검토. 재고 동시성 테스트 계획 추가 |
| T-6 | 🟢 | 제목에 "-임시"가 붙어 있음 | 버전을 확정하고 "임시" 표기 제거 |

## 02. 인프라 설계

| ID | 우선 | 보완점 | 제안 |
|---|---|---|---|
| I-1 | 🟡 | 그림에서 **LoadBalancer가 Gateway와 서비스 사이의 별도 서버처럼 보임**. 실제로는 Gateway와 각 서비스(Feign) **안에서 동작하는 라이브러리** | LB 박스를 Gateway 내부로 옮기거나 "client-side" 표기. 서비스 → 서비스 Feign 호출선 추가 |
| I-2 | 🟡 | **서비스 간 호출 경로(Feign)가 그림에 없음**. Order → Hub, Order → Delivery 등 Saga 흐름이 보이지 않음 | Order → Hub / Company / Delivery, Delivery → Hub 호출선을 점선으로 추가 |
| I-3 | 🟡 | `/internal/v1` **보호 방식이 없음**. Gateway에서 막는지, 서비스 간 인증을 어떻게 하는지 미정 | Gateway 라우팅에서 `/internal/**` 차단 + 내부 호출 헤더(예: 서비스 토큰) 검증 방식 명시 |
| I-4 | 🟢 | Prometheus·Grafana·Zipkin 컨테이너가 Compose 구성에 보이지 않음 | 실제로 띄울 컨테이너 목록과 포트 표 추가 (docker-compose 작성 기준) |
| I-5 | 🟢 | 단일 PostgreSQL에 스키마 5개. 요구사항은 **DB 계정 분리를 권장** | 서비스별 DB 계정 + 스키마 권한 구성 명시 |

## 03. 도메인 모델

| ID | 우선 | 보완점 | 제안 |
|---|---|---|---|
| D-1 | 🔴 | **재고를 어느 허브에서 차감하는지 규칙이 없음**. 재고는 (허브, 상품) 단위인데 주문에는 허브 정보가 없음. 배송의 **출발·도착 허브와 배송 주소를 정하는 규칙**도 없음 | 발제 예시 기준으로 명시:<br>• 차감 허브 = **공급업체의 관리 허브**<br>• 출발 허브 = 공급업체 관리 허브<br>• 도착 허브 = **요청업체의 관리 허브**<br>• 배송 주소 = 요청업체 주소<br>• 내부 재고 차감 API 요청에 `hubId` 포함 |
| D-2 | 🔴 | **P2P 모델과 경로 예시가 모순**. 발제는 "모든 허브 간 직접 배송 가능한 P2P"인데, DeliveryRoute 예시는 서울 → 대전 → 부산 **경유** | P2P면 배송 구간은 최대 2개: `HUB_TO_HUB` 1개(출발 ≠ 도착일 때) + `HUB_TO_COMPANY` 1개. 출발 허브 = 도착 허브면 `HUB_TO_COMPANY`만. 경유 예시는 삭제하거나 "확장 시" 표기 |
| D-3 | 🔴 | **배송 구간을 누가 언제 만드는지 불명확**. 발제는 "주문 생성 시 배송 경로 기록도 함께 생성"인데, API에는 관리자가 수동으로 구성하는 `POST /deliveries/{id}/routes`가 있음 | 배송 생성 시 Delivery Service가 Hub Service의 경로 조회 API로 **예상 거리·시간을 채워 구간을 자동 생성**. 수동 구성 API는 제거 |
| D-4 | 🔴 | **Saga 중간 실패 시나리오가 부족**. 정의된 것은 "재고 부족"과 "배송 생성 실패" 두 가지뿐 | 다음 경우를 추가 정의:<br>• 재고 차감 **응답 유실(타임아웃)** → 같은 멱등성 키로 재시도<br>• 배송 생성 후 **주문 COMPLETED 저장 실패**<br>• **보상(재고 복원) 자체의 실패**<br>• PROCESSING 상태로 **멈춘 주문의 복구** (부분 인덱스는 있으나 이를 처리할 스케줄러·정책이 없음) |
| D-5 | 🟡 | **주문 취소의 Saga가 없음**. 취소 시 재고 복원만 있고 **이미 생성된 배송의 처리**가 정의되지 않음 | 취소 흐름 정의: 배송 상태 확인 → 배송 취소(내부 API 추가) → 재고 복원 → CANCELLED. 취소 가능한 배송 상태 명시 |
| D-6 | 🟡 | 배송 상태(`deliveryStatus`)와 구간 상태(`routeStatus`)의 **값과 전이 규칙이 없음** (요구사항 DLV-06) | 상태 enum과 전이표 정의. 구간이 모두 완료되면 배송을 완료로 바꾸는 연동 규칙 포함 → [[07 서비스 정책]] 6.3 제안안 참고 |
| D-7 | 🟡 | 사용자와 업체를 잇는 방법이 **두 가지**: `User.organizationUuid`와 `Company.managerUserId`. 어느 쪽이 권한 판단 기준인지 모호 | "업체 수정 권한은 `managerUserId`만 기준, `organizationUuid`는 소속 표시용"처럼 역할 구분을 명시 |
| D-8 | 🟡 | **Slack 알림**이 도메인 모델에 없음. 수신자(공급업체 관리자? 배송담당자?)와 메시지 내용이 정의되지 않아 User의 `slack_id` 쓰임새가 불명확 | 알림 대상·발송 시점·실패 정책을 "외부 연동" 항목으로 추가 |
| D-9 | 🟢 | 제목 수준이 뒤집혀 있음: 그룹은 `####`, 엔티티는 `###` | 그룹 `###`, 엔티티 `####`로 정리 |

## 04. API 명세서

| ID | 우선 | 보완점 | 제안 |
|---|---|---|---|
| A-1 | 🔴 | **발제·요구사항과 다른 API**:<br>• 허브 수정 (발제: 조회만)<br>• 허브 경로 등록·수정·삭제 (발제: 조회만)<br>• `PATCH /users/me` (발제: 수정은 관리자만)<br>• 업체 등록 MASTER 전용 (발제: 업체 사용자 본인도 가능) | 발제 기준으로 제거하거나 튜터에게 확인 후 사유를 적어 유지 → [[07 서비스 정책]] 9장 |
| A-2 | 🔴 | **요구사항에 있는데 빠진 API**:<br>• 주문 논리 삭제 `DELETE /orders/{id}` (ORD-05)<br>• 배송·구간 논리 삭제 (DLV-05)<br>• 관리자 사용자 생성 (USR-04)<br>• 배송 취소 내부 API (D-5) | API 표에 추가 |
| A-3 | 🟡 | **요청·응답 본문이 없음**. "회원 및 소속 정보", "업체 변경 정보"처럼 서술만 있어 프론트엔드나 다른 서비스 담당자가 구현할 수 없음 (발제: "API 문서만 보고 개발 가능하게") | 핵심 API(회원가입, 로그인, 주문 생성, 내부 API 전부)부터 요청·응답 JSON 예시 작성. 발제 5단계 예시 형식 참고 |
| A-4 | 🟡 | **공통 응답·에러 형식이 없음**. 에러 코드, 페이지 응답 구조, 정렬 파라미터 형식이 정해지지 않음 | 공통 응답 포맷, 에러 응답(`code`, `message`), 페이지 응답, `sort=createdAt,desc` 규칙 정의 |
| A-5 | 🟡 | **Gateway → 서비스 사용자 정보 전달 방식이 없음** | `X-User-Id`, `X-User-Role` 같은 헤더 규약과, 외부에서 들어온 같은 이름의 헤더를 Gateway가 제거한다는 규칙 명시 |
| A-6 | 🟡 | 권한 표기가 정책과 다름:<br>• 주문 목록 "로그인" (정책: 본인만, MASTER는 전체)<br>• 재고 "관리자·허브담당" ("허브담당" 역할이 없음) | 권한 열을 [[07 서비스 정책]]의 권한표와 맞춤 |
| A-7 | 🟡 | 주문 생성 응답이 **`202 Accepted`(비동기)**인데 서비스 간 통신은 Feign **동기 호출** | 동기 처리 후 `201` + 최종 상태 반환으로 단순화하거나, 202 유지 시 처리 결과 조회 흐름을 명시 |
| A-8 | 🟢 | 끝부분에 **다른 프로젝트(배달 앱: 메뉴·결제·OWNER)의 API 표**가 섞여 있음 | 삭제 |

## 05. ERD · 06. 테이블 명세서

| ID | 우선 | 보완점 | 제안 |
|---|---|---|---|
| E-1 | 🔴 | **`p_orders`가 두 번 명세됨**(17컬럼 / 15컬럼 구버전). **`p_inventory_movements` 명세가 없음**. 그래서 "전체 12개 테이블"과 실제 명세가 맞지 않음 | 15컬럼 `p_orders` 삭제. `p_inventory_movements` 명세 추가 (ERD 이미지 기준 컬럼은 [[05 ERD]]에 반영됨). 총 컬럼 수 재계산 |
| E-2 | 🟡 | **UNIQUE와 Soft Delete가 충돌**. `username`, `(hub_id, product_id)`, `p_hubs.name` 등이 일반 UNIQUE라서 삭제된 행이 남아 있으면 **같은 값으로 다시 가입·등록할 수 없음** | 의도한 동작인지 결정. 재사용을 허용하려면 `UNIQUE ... WHERE deleted_at IS NULL` 부분 인덱스로 변경 |
| E-3 | 🟡 | **조회 패턴용 인덱스 누락**:<br>• 본인 주문 조회 `p_orders.ordered_by`<br>• 담당자 배송 조회 `p_deliveries.delivery_manager_id`<br>• 기본 정렬 `created_at DESC` | 인덱스 추가 |
| E-4 | 🟡 | `delivery_status`, `route_status`에 **CHECK 제약이 없음** (명세에도 "미정"으로 적힘) | D-6에서 상태값을 확정한 뒤 CHECK 추가 |
| E-5 | 🟢 | `idempotency_key` 길이가 다름: `p_inventory_movements`는 VARCHAR(100), history 테이블 2개는 VARCHAR(120) | 하나로 통일 |
| E-6 | 🟢 | **초기 데이터 계획이 없음**: 허브 17개, P2P 경로 17×16 = **272개**의 거리·소요시간 출처 | 시드 데이터 작성 방법 명시 (예: 지도 API로 1회 계산 후 SQL/CSV 적재) |
